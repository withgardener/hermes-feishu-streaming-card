# V4.3.0 Release Convergence Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Converge the completed Integration Core, Runtime Bridge, Hybrid Patch, and Installer Ownership milestones into a fully documented and automatically verified V4.3.0 release candidate without publishing it.

**Architecture:** Treat diagnostics and runtime readiness as consumers of already-owned facts, never as permission to mutate. Update public documentation only after focused behavioral gates pass, then bump all current-version markers together and prove the candidate with the full suite, cross-platform source contracts, wheel/sdist provenance, and an explicit real-Feishu evidence boundary.

**Tech Stack:** Python 3.9–3.12, aiohttp, pytest, setuptools build artifacts, POSIX shell, PowerShell, Docker Compose, GitHub Actions documentation contracts.

## 2026-08-13 Fixed-tag correction gate

This gate corrects release execution against the current repository and Hermes
`v2026.8.3` commit
`3c27eb6234bf91b8ceee9e9071591b31e9b148cb`; it does not widen publication
authority. **Tasks 1–6 are not executable until** Runtime has a signed
production bootstrap plus real fixed-tag plugin-manager subprocess proof,
Hybrid has provenance-bound target-aware aggregate proofs, and Installer has
passed its compensation/legacy/maintenance gates. Conflicting examples below
are superseded.

1. **Use the release verifier that exists.** The current test is
   `tests/unit/test_release_gate.py`, not `tests/unit/test_verify_release.py`.
   The current CLI accepts `--tag`, optional `--expected-commit`,
   `--require-main-ancestor`, and `--metadata-only`; it has no `--dist-dir` or
   `--version`. Candidate metadata is checked only after Task 3 has bumped all
   version markers, with:

   ```bash
    .venv/bin/python scripts/verify_release.py --tag v4.3.0 --metadata-only
   ```

   Task 2 therefore tests the Python API against temporary fixture markers; it
   must not run the repository metadata command while the checkout is still
   pre-bump. Exact sdist/wheel filenames and counts must be asserted separately after
   `python -m build`; wheel contents and ordinary `site-packages` provenance
   are proved by isolated install. Do not silently extend the verifier merely
   to make the obsolete command pass unless that extension receives its own
   RED/GREEN contract in `tests/unit/test_release_gate.py`.
2. **Only list files that exist or are explicitly created.** This repository
   has `README-install.md` but no `README-install.en.md`; remove the latter from
   Task 3 Files and `git add`. English install guidance belongs in the existing
   `README.en.md` unless a separately approved documentation change creates a
   new file and adds a docs test. Before every bulk `git add`, resolve the list
   with `git ls-files`/`test -e`; an absent path is a release-gate failure, not
   evidence to ignore.
3. **A clean wheel smoke is not the Hermes proof.** In addition to isolated HFC
   import/CLI checks, reuse the Runtime plan's regular-wheel fixed-tag
   subprocess: temporary explicit `HERMES_HOME`, exact `plugins.enabled`, real
   `PluginManager.discover_and_load`, signed Sidecar `/events`, runtime
   hello/heartbeat, callback execution and bounded close. The subprocess must
   be mandatory and non-skipped in the release gate; a fixture/TestClient
   callback sequence is insufficient. Its fixed-tag capability result remains
   exact 4 true / 9 false, and Hybrid is supported only when the exact 17 patch
   groups include `subagent_parent_identity`; native `subagent_lifecycle`
   remains unavailable.
4. **Local RC and publication are separate authorization boundaries.** Tasks
   1–6 may produce only a local release candidate and readiness evidence. They
   must not push, merge, create a tag/Release, upload assets, or send a real
   Feishu message. A later explicitly authorized publication run must verify
   the exact merge SHA on `origin/main`, green CI on that SHA, create an
   annotated `v4.3.0` tag at that SHA, run the real non-metadata verifier with
   `--expected-commit <40-hex> --require-main-ancestor`, upload exactly one
   wheel and sdist plus SHA-256 checksums, verify downloadable assets, and prove
   a public regular-wheel install imports from `site-packages`. Real
   Feishu/Lark acceptance remains a separate credentialed status and may be
   `UNVERIFIED`; it cannot be inferred from publication or automated tests.
   The repository's release-assets workflow additionally produces the existing
   macOS/Linux bundle names documented in `docs/wiki/release-playbook.md`; an
   authorized publication must verify those workflow assets and their
   checksums too, rather than treating the Python wheel/sdist pair as the full
   GitHub Release asset set.
5. **Corrected dependency order:** prior milestone correction gates → Release
   Task 1 diagnostics → Task 2 using `test_release_gate.py` → Task 3 existing
   docs only → Task 4 focused gates including real plugin-manager subprocess →
   Task 5 full suite/build/metadata/wheel evidence → Task 6 read-only local-RC
   audit. Stop at `PUBLICATION: NOT AUTHORIZED` unless new authority is given.

## Global Constraints

- This plan depends on every prior V4.3.0 implementation plan being green; it must not hide a failed runtime, ownership, fail-open, fail-closed, or recovery invariant with documentation changes.
- `native-hooks` remains a future capability path; current Hermes v0.20 selects `hybrid` only from the reviewed four native capabilities plus all 17 corrected patch groups, so public copy must not claim zero-patch operation.
- `doctor` distinguishes selected capability mode, effective plugin activation, installed manifest state, and runtime registration; “detectable” is not “healthy”.
- `doctor --json`, `/health`, runtime heartbeat, cards, and logs never expose raw Hermes home/config paths, config backup IDs, chat/message/session identifiers, secrets, answers, tool arguments, or secret-derived values.
- Runtime readiness facts do not grant mutation authority and do not restart Gateway.
- Package version is exactly `4.3.0`; tag spelling in current public install examples is exactly `v4.3.0`.
- Legacy release notes remain historical and are not mechanically rewritten.
- The automated release gate is `.venv/bin/python -m pytest -q` followed by `git diff --check`.
- Real Feishu/Lark smoke requires explicit credentials and target chat; fixtures cannot be reported as real-smoke evidence.
- Push, pull request, merge, tag, GitHub Release, and public asset publication require separate authorization and are outside this implementation plan.
