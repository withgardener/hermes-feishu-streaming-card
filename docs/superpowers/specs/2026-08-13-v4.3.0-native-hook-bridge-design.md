## 2026-08-13 Fixed-tag correction gate

本节只纠正 Hermes `v2026.8.3` commit
`3c27eb6234bf91b8ceee9e9071591b31e9b148cb` 下的可执行设计，不改变下文已批准的
产品结果。Integration Core 与 Runtime Bridge Tasks 1–5 的已完成事实保留；Runtime

不得据其转绿或验收。

### Runtime 和 capability 证据

- `hermes_plugin.register(ctx)` 负责 production bootstrap：从 installed runtime
  配置构造进程级 `PluginRuntime`，使用 private transport root 对 canonical JSON
  `/events` 请求调用 `sign_event_request`，调用 `configure_plugin_runtime` 后注册
  callbacks，并启动既有 signed runtime hello/heartbeat。replacement、partial
  bootstrap failure 与进程 shutdown/`atexit` 必须有 bounded、exactly-once close；
  session reset/finalize 只清理 session，不能关闭进程 runtime。
- `NativeHookCapabilities` 必须验证 entry-point discovery、`plugins.enabled`、真实
  `PluginManager` register 结果、每个 hook 的 source/AST callsite、actual kwargs、
  timing 和 return-value 语义。`pre_llm_call`/`post_llm_call`/`on_session_end` 的真实
  fixed-tag callsite 在 `agent/turn_context.py`/`agent/turn_finalizer.py`；approval 在
  `tools/approval.py`，原 observer kwargs 不含 HFC 所需的 exact turn/tool identity。
  `VALID_HOOKS`、版本字符串或手工 `PluginContext` 调用都不构成 available 证据。
  已复核结果保持 exact 4 true / 9 false：`turn_start`、
  `turn_terminal_result`、`stable_tool_lifecycle`、`approval_observe` 为 true；
  native `subagent_lifecycle` 为 false。
- 必须有真实 subprocess proof：regular HFC wheel 安装到 fixed-tag runtime、临时
  explicit `HERMES_HOME` 中 exact plugin enable、真实 `PluginManager` discovery/
  register、signed loopback Sidecar 请求、hello/heartbeat、真实 hook callsites、
  worker/heartbeat bounded close。TestClient 或手工 callback 驱动只算补充测试。

### 唯一 UI owner、canonical turn 和 terminal

- canonical `turn_id` 在 `agent/turn_context.py` 的真实创建点发布到 scoped carrier，
  在 `agent/turn_finalizer.py` 的匹配边界清除。Ingress、approval、clarify、slash 和
  terminal 只接受该 carrier 或 callsite 明确传入的 exact id；不得按 session 的
  recent/latest/single candidate、时间或插入顺序猜测。
- Approval 在 Hermes 原 `_await_gateway_decision` 创建 `_ApprovalEntry` 后、原
  `pre_approval_request` 前增加 exact prehook correlation；HFC 只 resolve 该 entry，
  原 FIFO loop 是唯一 wait。Clarify 保留原 register/wait 并 exact resolve；slash
  保留原 async register/future 并 exact resolve。Sidecar admission 原子选择 HFC
  UI，失败时不消费原 pending handle，native UI exactly once。禁止第二个 wait、
  queue、future、interaction request 或宽松 choice lookup。
- Terminal 对 exact turn 原子保存 canonical payload 和第一次 canonical response；
  唯一 retry 必须复用同 payload/event id/sequence 并取得该记录。只有 successful
  `message.completed` 的严格 card disposition 可 suppress；`message.failed`、
  interrupted、无 answer、missing/malformed/timeout/exception 永不 suppress。
  `disposition=native` 必须通过既有 exact descriptor validator（exact keys/types、
  protocol、id、seed、expiry、turn binding），不得另写宽松 validator。Transport
  返回、retry eligibility 和 record commit 各使用 fresh monotonic time 验证 expiry；
  阻塞 `post()` 期间过期的 descriptor 不得缓存为有效 response。

### Fixed-tag patch、installer 和 release 边界

- v0.20 fixture 必须由 fixed-tag source 机械提取并记录 commit、relative path、
  完整 source SHA-256、slice/anchor provenance；不得发明 `_hfc_*` locals 或不存在的
  Gateway 方法。Patch groups 按 target 聚合，至少覆盖 `gateway/run.py`、
  `agent/turn_context.py`、`agent/turn_finalizer.py`、`tools/approval.py`、
  `cron/scheduler.py`、`gateway/platforms/base.py`、`tools/delegate_tool.py`；后者
  承载必需的 `subagent_parent_identity` group，使 background stop 消费 start 已保留
  的 immutable parent turn。跨 mode 只消费 installer 对每个
  target 的 identity/current hash/backup hash 验证过的 original bytes，不能把
  `remove_patch(installed)` 自称 verified original。
- POSIX venv Python 通常是 symlink：binding 同时校验 lexical link 和 resolved
  regular executable，并在 `-I` probe 中校验 `sys.executable`、`sys.prefix`、
  `sys.base_prefix`、purelib/platlib 和 entry-point origin。Config/home/private state
  仍禁止 symlink。Installer 从首次 preimage/journal 写起使用一个 staged
  compensation transaction，覆盖 phase/config/每 target/manifest/final-probe 全部
  fault points；无法安全补偿时保留 truthful recoverable evidence。
- V1/V2/支持的 manifestless Legacy restore/uninstall 先走 verified source-only 分支，
  不要求新 binding 且不修改 plugin config；V2→V3 migration 才要求 binding 和
  aggregate verified originals。Maintenance job 用 opaque `binding_ref` 解析私有
  no-follow registry 中的目标，再全量复核 identity；hash-only job 不可执行。
- Release 自动 gate 使用真实 `tests/unit/test_release_gate.py` 和
  `scripts/verify_release.py --tag v4.3.0 --metadata-only`；当前不存在
  `README-install.en.md`。本计划最多产出 local RC。Merge、annotated tag、assets/
  checksums、public regular-wheel install 与 real Feishu acceptance 都是后续独立
  授权和独立证据边界。

## 目标

V4.3.0 将 HFC 从“所有生命周期都依赖 `gateway/run.py` patch”迁移为
“Hermes 官方 plugin hooks + 仍然必要的最小 patch”。

本版本的产品结果是：

- Hermes 官方 hook 成为 turn、tool、approval、subagent 生命周期的首选来源；
- 流式 delta、交互选择回传、命令卡、原生灰字抑制和 exact delivery 仍由
  可验证、可逆的最小 patch 承担；
- 安装器按实际能力选择 `native-hooks`、`hybrid` 或 `legacy-patch`，不只按
  版本号猜测；
- Hermes v0.20 / `v2026.8.3` 默认进入 `hybrid`；
- 当前仍支持的较老 Hermes 版本继续通过 `legacy-patch` 工作；
- 安装、Hermes 升级、恢复和卸载都保留可验证所有权，并在证据不确定时
  fail-closed；
- `doctor --explain` 能说明“为什么选择这个模式”“plugin 是否真的加载”以及
  “还剩哪些 patch”。

V4.3.0 的完成标准是实现、自动化测试、文档和可执行验收准备全部完成。未经
额外授权，本工作不 push、不创建 tag、不发布 GitHub Release。

## 背景与证据

Hermes v0.20 提供 pip entry-point plugin、`register(ctx)` 和一组正式生命周期
hook。与 HFC 相关的正式参数已经包括：

- `pre_llm_call`：`session_id`、`task_id`、`turn_id`、`platform`；
- `post_llm_call`：同一组身份、最终 `assistant_response`；
- `on_session_end`：`completed`、`failed`、`interrupted`、
  `turn_exit_reason`；
- `pre_tool_call` / `post_tool_call`：`session_id`、`task_id`、`turn_id`、
  `tool_call_id`，结束时还有 `duration_ms`、`status` 和错误分类；
- `pre_approval_request` / `post_approval_response`：`session_key`、surface、
  command 和最终 choice；
- `subagent_start` 保留 originating parent turn；background `subagent_stop` 当前读取
  mutable `parent_agent._current_turn_id`，所以 exact parent identity 必须由
  `subagent_parent_identity` patch group 修正；其余参数包括子 session、role、status
  和耗时。

这些接口足以替代 HFC 当前对 tool 和大部分 turn 生命周期的局部变量抽取，
但还不能替代：

- `answer.delta` 和 `thinking.delta`；
- clarify、slash confirmation 和 approval choice 的同步回传；
- Gateway 最终回答的卡片接管与 native text suppression；
- command card、platform notice、context compaction 和 cron delivery；
- Base adapter exact delivery、native handoff ACK 和 redelivery recovery。
- background subagent stop 的 immutable parent turn identity。

因此 V4.3.0 不宣称“零 patch”。它先建立稳定的 Hybrid 架构，并把未来删除
patch 所需的 capability selector 和测试契约放到位。

## 设计原则

1. **一个事件只有一个权威生产者。** Hybrid 下官方 hook 负责的生命周期，
   patch 不再重复发送。
2. **Hermes `turn_id` 是唯一 turn 主键。** HFC 不再为新模式制造第二套业务
   turn id。
3. **鉴权前不建立路由。** `pre_gateway_dispatch` 位于 Hermes auth 之前，不能
   被用来创建可投递的 Feishu route binding。
4. **运行时 fail-open，安装时 fail-closed。** HFC 故障不能阻断 Hermes；所有权、
   capability 或目标身份不清楚时不能修改文件或配置。
5. **能力优先于版本。** 版本只用于解释和最低支持判断，模式由已验证接口决定。
6. **同一个 wheel 是唯一 plugin 代码。** 避免包与复制目录发生版本漂移。
7. **敏感信息不进入 manifest、日志或健康接口。** 必须保存的 Hermes config
   精确备份仅存在于受控本地状态，权限为 `0700/0600`。
8. **不扩大 patch。** 每个保留 patch 都要对应一个当前官方 API 无法完成的
   明确能力。

## 1. 组件边界

### `hermes_feishu_card/integration.py`

这是无副作用的兼容性模型，包含：

- `IntegrationMode`：`native-hooks`、`hybrid`、`legacy-patch`；
- `NativeHookCapabilities`；
- `PatchCapabilities`；
- `IntegrationDecision`；
- `select_integration_mode(...)`；
- capability fingerprint 的规范化和哈希。

该模块不读文件、不导入 Hermes、不发 HTTP，方便对所有组合做纯单元测试。

### `hermes_feishu_card/install/plugin.py`

该模块负责安装侧 plugin 能力和配置所有权：

- 用 Hermes runtime Python 的 isolated subprocess 探测 `VALID_HOOKS`；
- 检查 entry point 的 group、key、module、distribution、version 和 import origin；
- 解析并绑定准确的 `HermesRuntimeBinding`；
- 调用 Hermes 官方 plugin enable 机制；
- 保存、验证和恢复 plugin config preimage；
- 为 manifest 和 recovery 提供不含秘密的结构化结果。

它不注册 hook，也不发送 Sidecar event。

### `hermes_feishu_card/hermes_plugin.py`

这是 wheel entry point，只暴露：

```python
def register(ctx) -> None:
    ...
```

它验证 Hermes 提供的 hook 名称并将 callback 注册到
`hermes_plugin_runtime.py`。模块导入不得执行网络、文件修改或 Hermes 私有对象
monkeypatch。

### `hermes_feishu_card/hermes_plugin_runtime.py`

该模块拥有新模式的运行时协调：

- `IngressBindingRegistry`；
- `TurnBinding` 和 generation/expiry；
- 官方 hook 参数归一化；
- plugin 与最小 patch 共用的 per-turn sequence；
- 确定性 `event_id`；
- terminal disposition 缓存；
- approval pending binding；
- bounded cleanup 和 sanitized diagnostics。

它复用现有 event authentication、delivery policy、transport 和 Sidecar endpoint，
不复制 renderer 或 Feishu client。

### `hermes_feishu_card/hook_runtime.py`

保留 patch-only 能力和现有 Feishu adapter 包装。V4.3.0 新增的桥函数必须是薄的：

- 鉴权后 ingress binding；
- answer/thinking delta 提交给共享 turn coordinator；
- clarify、slash confirm 和 approval choice 等待/回传；
- terminal delivery disposition 消费；
- command、notice、cron 和 exact delivery 现有路径。

官方 hook 已负责的 tool/turn 生命周期不得再从这里重复生产。

### Sidecar

`events.py`、`server.py`、`session.py` 和 `render.py` 继续拥有事件验证、card
session、去重、渲染和 Feishu delivery。它们不导入 Hermes plugin API。

## 2. Plugin 分发和注册

`pyproject.toml` 增加：

```toml
[project.entry-points."hermes_agent.plugins"]
hermes-feishu-card = "hermes_feishu_card.hermes_plugin"
```

选择 entry point 而不是目录 plugin 的原因：

- HFC 已经必须安装到 Hermes venv；
- entry point 与 CLI、hook runtime 的版本天然一致；
- wheel、Docker、macOS、Linux 和 Windows 共用一条路径；
- restore/uninstall 不需要删除第二份代码目录；
- Hermes 官方支持通过 `importlib.metadata` 发现 pip plugin。

Plugin key 固定为 `hermes-feishu-card`。安装探针必须证明：

- entry point group 恰好是 `hermes_agent.plugins`；
- key 恰好匹配；
- value 恰好指向 HFC 的公开 entry module；
- distribution 是 `hermes-feishu-streaming-card`；
- distribution version 与当前 CLI `PACKAGE_VERSION` 相同；
- isolated import 来自绑定 Hermes venv 的普通 `site-packages`，不是 checkout、
  editable install 或其他 Python 环境。

任何同名 entry point 劫持、重复候选、版本或 import origin 不匹配都使
Hybrid/Native 安装失败。Legacy 模式可以发现 entry point，但 plugin callback
必须因没有 active Hybrid binding 而 no-op。

Wheel provisioning 位于 integration mutation 事务之前。现有一键安装器和
`_ensure_hermes_runtime_package` 可以先把当前 HFC 普通 wheel 安装/升级到 Hermes
venv；pip 本身不属于 checkout/config 的跨目录恢复事务。后续 integration 失败
时不尝试自动 pip downgrade 或卸载正在执行的包，而是必须收敛到：

- plugin config 恢复到 preimage；
- 没有 HFC-owned source patch；
- entry point 即使仍可发现也未有效启用，callback no-op；
- manifest/journal 如实报告 `package_provisioned` 或待人工检查，不能声称安装成功。

这与现有安装器“先确保 runtime package，再安装 hook”的边界一致，并避免一个
不可靠的包管理回滚覆盖用户环境。

Plugin 注册以下官方 hook：

- `pre_llm_call`；
- `post_llm_call`；
- `on_session_end`；
- `on_session_reset`；
- `on_session_finalize`；
- `pre_tool_call`；
- `post_tool_call`；
- `pre_approval_request`；
- `post_approval_response`；
- `subagent_start`；
- `subagent_stop`。

每个 callback 返回 `None`。HFC 不注册 tool，不返回 plugin directive，不申请
tool override。未知 kwargs 通过 `**kwargs` 安全忽略，便于 Hermes 向前兼容。

Hermes 的 plugin manager 同步调用 callback。HFC 将 callback 分为两类：

- tool、approval terminal、subagent 等观察事件可提交给有界、按 turn 排序的
  worker；队列满或 worker 不可用时丢弃 HFC event 并 fail-open；
- `pre_llm_call` 的 `message.started` 和 `on_session_end` 判定的 terminal 必须在
  callback 内完成有界同步 authenticated request，取得 Sidecar 明确结果后再
  返回。`post_llm_call` 只提供最终文本，不能证明 turn 成功；它将文本短暂保存到
  exact turn-local 缓存，供紧随其后的 `on_session_end` 使用。二者都不能
  fire-and-forget，因为后续 Gateway native suppression bridge 需要同一 turn 的
  terminal disposition。

同步请求复用现有 transport timeout 和 sanitizer，不能无限阻塞 Hermes。超时、
异常、不可解析 response 或 Sidecar 拒绝时不缓存成功 disposition，Hermes 随后
走原生路径。

## 3. Capability 探测和模式选择

### Native hook capabilities

V4.3.0 识别以下能力类别：

- authenticated ingress / route context；
- turn start；
- turn terminal result；
- stable tool lifecycle；
- approval observe；
- subagent lifecycle；
- answer delta；
- thinking delta；
- clarify / approval / slash interaction round-trip；
- final delivery disposition / native suppression；
- command and platform notice；
- cron delivery；
- exact native delivery ACK and recovery。

Hermes v0.20 的官方 plugin API 覆盖其中一部分，而不是全部。V4.3.0 不为未知
未来接口发明名称。`native-hooks` 选择器有完整的纯测试契约，但只有 detector
明确识别到所有必要正式能力时才可选择。对当前 v0.20，该模式不可达。

### Patch capabilities

Patch detector 按 group 验证 AST anchor、局部变量和可逆性，而不是只返回
“run.py 可 patch”：

- `ingress_binding`；
- `terminal_disposition`；
- `answer_delta`；
- `thinking_delta`；
- `clarify_round_trip`；
- `approval_round_trip`；
- `status_notice`；
- `slash_confirm`；
- `command_card_startup`；
- `command_card_adapter`；
- `native_redelivery`；
- `platform_notice`；
- `hfc_command`；
- `cron_delivery`；
- `exact_base_no_text`；
- `exact_base_final_delivery`。
- `subagent_parent_identity`。

Legacy detector 继续验证现有完整 patch 所需的 started、completed、queued
completed 和 tool callback groups。

### 决策顺序

模式选择优先级是：

1. 所有正式能力均可验证：`native-hooks`；
2. exact 四项已复核 native capability 且全部 17 个 Hybrid 必要 patch group 可验证：`hybrid`；
3. 完整 Legacy patch group 可验证：`legacy-patch`；
4. 以上均不成立：unsupported，拒绝 mutation。

因此：

- Hermes v0.20 / `v2026.8.3` 预期为 `hybrid`；
- fixed-tag probe 保持 4 true / 9 false，Hybrid 由
  `subagent_parent_identity` patch 补足 exact parent identity；
- 当前支持的 v0.19 及更老 Hermes 在完整 anchor 存在时继续为
  `legacy-patch`；
- v0.20 某个官方 hook 缺失但 Legacy anchors 完整时可降级 Legacy；
- 不能因为 HTTP 200、版本字符串或存在 `VALID_HOOKS` 就宣称 Hybrid；
- source-stripped Docker 必须通过 runtime probe 和可逆 AST anchor 取得等价
  证据，否则拒绝安装。

`HermesDetection` 增加：

- `integration_mode`；
- `plugin_api`；
- `native_hook_capabilities`；
- `patch_capabilities`；
- `plugin_entrypoint`；
- `plugin_enabled`；
- `capability_fingerprint`；
- 结构化的 mode reason。

`integration_mode` 表示能力支持的计划模式；entry point 和 enable 字段表示当前
runtime 是否已经实际激活。`doctor` 不会把“可安装”写成“已启用”。

## 4. Hybrid Patch 所有权

### Hybrid 保留

Hybrid 只保留官方 API 当前无法替代的 group：

- 鉴权后 ingress binding；
- terminal delivery disposition 消费和 native suppression；
- answer/thinking delta；
- clarify、approval choice、slash confirm 的交互回传；
- status/context compaction；
- command card startup/adapter；
- native redelivery；
- platform notice 和 `/hfc` command；
- cron delivery；
- exact Base delivery / ACK / recovery。
- subagent background stop 的 immutable parent identity 修正（
  `subagent_parent_identity`，不生产 lifecycle event）。

### Hybrid 删除

以下事件不得再由 patch 生产；`subagent_parent_identity` 只纠正 identity，不属于
producer：

- `message.started`；
- 普通成功/失败 turn terminal 生命周期；
- stable tool start/stop；
- legacy progress tool lifecycle；
- subagent lifecycle；
- approval observer 状态。

现有 start/complete/tool marker 不能简单保留后在运行时去重。Patcher 必须根据
mode 生成不同的 marker 集合，从源头保证唯一生产者。

### Patcher API

Patcher 增加显式 mode/group API，不能通过环境变量隐式决定：

```python
apply_patch(
    content: str,
    strategy: str = "legacy_gateway_run",
    *,
    integration_mode: str = "legacy-patch",
) -> str
remove_patch(content: str) -> str
detect_patch_groups(content: str) -> frozenset[str]
```

以上单 target API 仅保留 Legacy/backward-compatible primitive；V4.3 Hybrid 与
installer 的 authoritative API 必须是 target-aware aggregate：输入
`Mapping[relative_target, bytes]`，输出/检测
`Mapping[relative_target, frozenset[group]]`，并对整组 apply/remove/verify。
已完成 selector 的 `IntegrationDecision.required_patch_groups` 继续表示 flat logical
set；descriptor registry 的 target mapping union 必须与它完全相等，manifest 同时
记录两者，避免重写 Integration Core 已完成契约。

`remove_patch` 从受严格校验的 marker 自描述实际 group，不信任外部 mode 参数，
从而保持现有调用兼容并避免 manifest 谎报导致漏删。安装器按 target 将 aggregate
detector 结果与 manifest 的 target→exact group mapping 比较，不能只检测
`gateway/run.py`。以上 API
必须满足：

- 同一输入和 mode 幂等；
- 每个 marker body 可严格校验；
- `remove(apply(original)) == original`；
- 从 Legacy 迁移 Hybrid 时，从 verified original/backup 重渲染，不在旧 patch
  上叠加；
- manifest 只声明实际存在的 group；
- corrupt、duplicate 或未知 marker 拒绝 mutation。

## 5. 事件绑定与数据流

### 鉴权后 ingress binding

Hermes `pre_gateway_dispatch` 在 auth/pairing 之前触发。V4.3.0 不用它建立路由、
发卡或缓存可投递身份。

最小 `ingress_binding` patch 位于 Hermes 已完成消息准入、准备调用 agent 的真实
路径。它只向 bridge 传递该 callsite 已验证存在的明确值；下面旧的 locals 形式被
本文件 fixed-tag correction gate 取代，不得作为 anchor 或 fixture：

```python
bind_ingress_from_hermes_locals(locals())
```

绑定必须包含可验证的：

- platform 为 Feishu/Lark；
- profile id 和其来源；
- chat id、incoming message id、reply anchor、thread id；
- Hermes session key；
- agent `session_id`；
- Gateway run generation 或等价 current-run fence。

它不发送 `message.started`。非 Feishu、身份不全、未知 profile source、旧 run 或
并发 binding 均 no-op/fail-open。

Registry 按 `(profile, Hermes session_id, generation)` 保存短生命周期 binding。
同一 Hermes session 的新 generation 取代旧 ingress；terminal、reset、finalize、
超时和有界清理都会删除状态。

### Turn 建立

`pre_llm_call` 在授权后的 agent turn 中取得正式 `session_id`、`task_id` 和
`turn_id`。它只能 claim 一个与该 session/generation 精确匹配的 ingress：

1. 创建 `TurnBinding`；
2. 将 Hermes `turn_id` 设为 canonical turn id；
3. 固定本轮 delivery policy；
4. 发送唯一 `message.started`；
5. 保存本轮 sequence/event identity coordinator。

没有唯一 binding 时 callback 返回 `None`，不猜 chat、不使用“最近一条消息”，
也不影响 Hermes 原生回复。CLI、ACP、Kanban worker、非 Feishu Gateway 等没有
Feishu ingress 的官方 hook 因此天然 no-op。

`TurnBinding` 使用显式单向状态机：

```text
pending-start -> card-active -> terminal
              -> native-bypass -> terminal
```

- 只有 Sidecar 对确定性 started event 返回结构完整的 `ok=true`、
  `applied=true`，turn 才进入 `card-active`；
- delivery policy 明确要求 native、Sidecar 明确拒绝、started 重试后仍 timeout/
  unknown，turn 都进入 `native-bypass`；
- `native-bypass` 后 tool、delta、approval 和 subagent event 全部不再发送；
- started 使用同一 `event_id` 做一次有界重试，Sidecar event-id fence 对已完成的
  首次请求返回相同结果；
- 状态不能从 `native-bypass` 回到 `card-active`，也不能从 `terminal` 重新打开。

即使 started 结果不确定，成功终态仍允许一次使用同一 turn route 的确定性
`message.completed` reconciliation。Sidecar 可以更新已创建但 ACK 丢失的卡，或
按既有 completed-without-started 语义创建最终卡。只有该 terminal 明确返回
`applied=true` 才抑制 Hermes native answer；terminal 仍不确定时优先保证内容
可见，走 Hermes native delivery。此边界不能宣称跨进程故障下数学上的 exactly
once；它保证 HFC 不会发送两份完整 terminal event，且不以不确定结果吞掉答案。

### Tool lifecycle

`pre_tool_call` 和 `post_tool_call` 使用 Hermes 提供的 `turn_id` 和
`tool_call_id` 生成一个工具项的 start/terminal 状态。要求：

- `tool_call_id` 为空、turn binding 不存在或 turn 不是 `card-active` 时不发送；
- `post` 可独立补齐缺失的 `pre`，但仍使用同一确定性身份；
- `status`、`duration_ms`、error classification 使用 Hermes 正式字段；
- 不把原始 args/result、conversation history 或 exception body直接发送；
- 仅复用现有 allowlist 和 sanitizer 生成有界 preview；未知工具只显示名称和
  状态；
- callback 永远不返回 block/approve directive。

### Answer 和 thinking delta

最小 patch 继续捕获正式 streaming callback，但不自己选择 route 或 sequence。
它按当前 Hermes turn 调用共享 coordinator。无 active TurnBinding 时返回 false，
让 Hermes 保留原有行为。

这里的 active 明确指 `card-active`；`pending-start`、`native-bypass` 和 `terminal`
都不能发送 delta 或返回“卡片已接管”。

### Terminal decision and delivery

Hermes `v2026.8.3` 的 `post_llm_call` 只证明存在非空、未中断的最终文本，不证明
`completed=true` 或 `failed=false`。因此 `on_session_end` 是唯一 terminal 判定点：

1. `post_llm_call` 只为 exact `turn_id` 缓存最终 `assistant_response`；
2. `on_session_end` 仅在 exact active turn 且 `completed=true`、`failed=false`、
   `interrupted=false` 时构造 `message.completed`；failed/interrupted 构造唯一
   `message.failed`；缺 `turn_id` 的 safety callback 只做保守 cleanup；
3. 向 per-turn worker 放入 barrier，并在有界时间内等待 barrier 前的 delta/tool/
   subagent event；若超时则封闭队列、丢弃尚未投递的观察事件并继续 terminal；
4. 发送确定性的 `message.completed` 或 `message.failed`；
5. 保存 Sidecar 返回的 `applied` / native handoff disposition；
6. 将 turn 原子地标为 `terminal`，拒绝所有迟到 worker item；
7. 不修改最终回答文本。

完整 answer 只有一个严格例外可跨 callback 暂存：exact `turn_id` 的 turn-local、
短 TTL、有界条目，只供紧随其后的 `on_session_end` 和同 event-id terminal retry；
不得进入日志、health、metrics 或 registry dump，并在 terminal/reset/finalize/expiry
后清除。完成判定时若没有 exact cached answer，必须 fail-open 到 Hermes native，
不能猜内容或使用别的 turn 文本。

`on_session_end` 的终态收口：

- 成功 terminal 已确认时只做 cleanup；
- 成功 terminal 未确认时用同一 `event_id` 重试一次；
- failed/interrupted 时发送唯一 `message.failed`，只包含白名单状态和
  `turn_exit_reason` 分类；
- terminal 后清理 turn route、approval 和 sequence 状态。

Terminal retry 不创建新 sequence 或新 payload；如果第一次 terminal 已到达
Sidecar，它必须从 event-id fence 获得同一 canonical result。两次都无法取得明确
结果时不缓存 success disposition，Gateway fail-open 到 native answer。

### Native suppression bridge

Gateway 完成 agent 调用后，`terminal_disposition` patch 只消费已由 plugin
产生的 terminal result：

- `applied=true` 且 card path 已接管：抑制 native gray text；
- `disposition=native` 且有 verified exact handoff descriptor：把 descriptor 放入
  现有 turn-scoped exact delivery context，随后由 Base adapter 发送并 ACK；
- 没有结果、结果超时、turn 不匹配或 Sidecar outcome 不确定：fail-open 到 Hermes
  native delivery；
- 不能在这个 patch 再发送第二个 `message.completed`。

这条桥是当前官方 `post_llm_call` observer 无法影响 Gateway delivery 的必要最小
patch。

### Approval

官方 approval hook 是 observer，不能直接把飞书选择返回 Hermes。Hybrid 分工是：

1. `pre_approval_request` 根据 `session_key`、`turn_id`、`tool_call_id` 和唯一
   active TurnBinding 创建 approval `interaction.requested` 与 pending choice；
2. 最小 approval patch 只等待这个 pending choice，并把结果交回原 Hermes
   approval callback；
3. `post_approval_response` 用 Hermes 最终 `choice` 更新/关闭 interaction；
4. exact `session_key`、turn、tool call、command fingerprint 或 surface 不能对应
   时回到 Hermes 原生审批；
5. HFC 绝不自动批准，Sidecar/bridge 失败按 Hermes 原生 deny/timeout 规则处理。

CLI/ACP/smart surface 没有 Feishu TurnBinding，因此仅观察不发卡。

### Clarify 和 slash confirmation

Hermes v0.20 没有等价正式 round-trip hook，继续由最小 patch 负责 request、等待
和选择回传。它们必须使用相同 TurnBinding 和 deterministic interaction id。

### Subagent lifecycle

`subagent_start` / `subagent_stop` 使用 `parent_turn_id` 关联父卡片，并发出
`subagent.updated`：

- identity 优先使用 `child_subagent_id`，否则使用 `child_session_id`；
- start 显示 role 和有界、脱敏的 goal preview；
- stop 显示 status、duration 和有界 summary preview；
- 不发送完整 tool history 到卡片、日志或 health；
- 找不到父 TurnBinding 时 no-op；
- 它与 `delegate_task` 工具调用是不同语义，renderer 显示为独立 subagent
  timeline item，不伪装成第二个 tool item。

V4.3.0 只做运行中 subagent lifecycle；Kanban task lifecycle 不在本版本。

`subagent.updated` 是 V4.3.0 新增的受支持 Sidecar event。`events.py` 必须显式
验证它，`session.py` 以 child identity 更新一个 timeline item，`render.py` 使用
与 tool 不同的 subagent 标识和状态。未知/旧 Sidecar 不能把该 event 当成成功
接管；plugin 必须 fail-open 且不能影响父 turn。

## 6. 事件身份、顺序和去重

`SidecarEvent` schema version 保持 `"1"`，新增向后兼容的可选字段：

- `event_id`；
- `producer`：`plugin`、`patch` 或 `legacy-patch`；
- `phase`；
- 已有的 `turn_id` 继续使用。

新字段必须是有长度上限的普通字符串。Legacy event 没有它们时继续走现有
sequence/session 语义。

Hybrid 的确定性 event id：

```text
turn:{turn_id}:started
tool:{turn_id}:{tool_call_id}:started
tool:{turn_id}:{tool_call_id}:terminal
approval:{turn_id}:{approval_fingerprint}:requested
approval:{turn_id}:{approval_fingerprint}:terminal
subagent:{turn_id}:{child_id}:started
subagent:{turn_id}:{child_id}:terminal
turn:{turn_id}:completed
turn:{turn_id}:failed
```

所有 plugin 和最小 patch producer 共享一个锁保护的 per-turn sequence。Sidecar
增加有界 TTL/LRU event-id fence：

- 同 event id、同 canonical payload：返回成功但不重复 apply；
- 同 event id、不同 canonical payload：拒绝并记录脱敏 conflict；
- terminal native handoff 继续使用现有持久化 descriptor/ACK fence，不由内存
  LRU 取代；
- cleanup 不得提前删除未解决 exact handoff 的持久化去重证据。

Worker item 在入队时取得 sequence；terminal barrier 记录最后允许的 sequence。
Barrier 之后的 item、terminal 后迟到的 callback 和旧 generation item全部丢弃。
`message.completed` / `message.failed` 的 sequence 必须严格大于 barrier 前所有已
接受观察事件。

从源头唯一生产者、确定性 id 和 Sidecar fence 三层共同避免双工具、双终态和
重复灰字；不能只依赖 UI 渲染时去重。

## 7. Runtime 错误与安全边界

所有 plugin callback：

- 捕获自身异常并写 sanitized debug；
- 返回 `None`；
- 不持有 Hermes live agent、gateway 或 session store 超过 callback；
- 不在 health/log 输出 raw chat、message、session、tool args/result、command 或
  answer；
- 不把 `conversation_history` 保存到 registry；
- 使用有界 registry、TTL 和 preview 长度；
- Sidecar timeout、auth failure、malformed response 或 route missing 时让 Hermes
  正常继续。

如果 `message.started` 尚未被 Sidecar 明确接受，后续 tool/delta/interaction/
subagent HFC event 不得发送或抑制 Hermes native delivery；只保留成功 terminal
reconciliation。若 card 已接管后更新失败，沿用现有 accepted/applied/native
handoff 语义，不能从不可解析响应推断成功。

Plugin 未加载、配置未启用或 entry point import 失败时，最小 patch 最多建立
短期 ingress binding；没有正式 turn/terminal disposition 就会 fail-open 到原生
Hermes。`doctor` 必须把这种状态报告为不可用，而不是“Hybrid 正常”。

## 8. Hermes Runtime Binding 和多 profile

一次 HFC `install/setup` 只绑定一个明确的 Hermes runtime：

```text
HermesRuntimeBinding
  checkout_root
  runtime_python
  python_identity
  hermes_home
  config_path
```

`HFC profiles.*` 是 Feishu bot/card 路由配置，不等于 Hermes 的多个
`HERMES_HOME`。安装器禁止根据 HFC `--profile-id` 猜测 Hermes config。

Binding 解析顺序：

1. 显式 `--hermes-home`；
2. 当前进程的 `HERMES_HOME`，前提是能证明它绑定指定 checkout/runtime；
3. 已支持的标准 parent-home layout，前提是候选唯一且 checkout、runtime、
   config identities 全部一致。

候选为零或多个时，Hybrid/Native mutation 拒绝并要求显式 `--hermes-home`。
运营多个 Hermes home/profile 时，必须分别对每个目标执行 install。所有 profile
相关 CLI、install.sh、install.ps1、doctor、restore、uninstall 和 maintenance
update 路径必须传递/保留同一个 binding。

## 9. Plugin 配置启用事务

Hermes entry-point plugin 默认 opt-in，必须出现在绑定 home 的
`plugins.enabled`。HFC 使用绑定 runtime 的官方 plugin enable 命令，并显式拒绝
tool override grant。

官方命令会分步写 config，无法与 checkout 中的 patch 做跨目录单次原子提交。
V4.3.0 使用可恢复的分阶段事务，而不是假装原子：

### Preflight

- 验证 runtime binding、config 文件身份、权限和非 symlink；
- 验证 entry point 和 capability decision；
- 验证所有目标源码、backup、manifest 和 parent identities；
- 读取 config 精确 bytes 和 SHA-256；
- 判断 plugin 是否原先已有效启用、是否显式 disabled，以及 HFC entry flag 的
  原状态。
- 将原始 Hermes config 解析成 normalized semantic tree，供写后差异校验；secret
  value 只在进程内比较，不进入输出或 journal。

### Prepared phase

在绑定 `HERMES_HOME` 的 HFC 私有目录创建：

- config preimage backup，mode `0600`；
- install journal，mode `0600`；
- 私有目录 mode `0700`。

备份可能包含 Hermes config 中的秘密，因此：

- 不放在 Git checkout；
- 不把内容、路径或 secret-derived value 写入 manifest、CLI output、日志、card
  或 health；
- manifest 只记录随机、固定格式的 `config_backup_id`、hash 和 binding 身份摘要，
  不记录 home-relative 或 absolute path；restore 在显式绑定的
  `${HERMES_HOME}` 私有 HFC 状态目录下解析该 id；
- restore 成功后安全删除；失败时保留并明确需要人工检查。

若已有 V1/V2/V3 manifest，prepared journal 还要保存它的精确 preimage、hash 和
文件身份。Checkout manifest 写入 `phase=prepared` 后才允许调用 Hermes config
writer；崩溃恢复只有在 current manifest 仍等于 prepared hash 时才可恢复旧
preimage。旧版 HFC 看到 v3 manifest 会拒绝 mutation。

### Enable phase

使用绑定 runtime Python、准确 `HERMES_HOME` 和非交互参数调用官方 enable：

- 添加 `hermes-feishu-card`；
- 清除会阻止它加载的同 key/alias disabled state；
- 不授予 `allow_tool_override`；
- 重新读取 config 并验证 plugin 实际可发现、有效启用；
- 比较写前/写后 normalized tree；允许的差异只有
  `plugins.enabled`、阻止同一 plugin 的 `plugins.disabled` alias，以及 HFC 自己的
  `plugins.entries.hermes-feishu-card.allow_tool_override=false`；任何其他语义变化
  都恢复 preimage 并拒绝继续；
- 将 config post SHA-256 和安全 ownership facts 写入 journal/manifest，进入
  `phase=plugin_enabled`。

官方 Hermes config writer 可以规范化 YAML 排版或移除注释。HFC 能证明业务
语义除上述 plugin 字段外未变，并能在 restore 时恢复精确 preimage，但不能承诺
安装期间保留原文件注释/排版；安装器必须在 mutation 前明确提示这一影响。

若 plugin 原先已有效启用且没有冲突，不改 config，记录
`enabled_before=true`、`added_by_hfc=false`。若 HFC 修改了 config，记录
`added_by_hfc=true`，同时保存精确 pre/post identity。

### Patch phase

根据 selected mode 生成源码、backup 和最终 manifest，通过现有绑定目录的安全
transaction 一次提交。随后 isolated probe 必须证明：

- plugin 从目标 site-packages 加载；
- plugin 已启用；
- active marker group 与 decision 完全一致；
- patch 严格可逆；
- final manifest 为 `phase=installed`；
- `doctor` 不会降级成另一模式。

任一步失败时：

- 源码 transaction 按现有规则回滚；
- config 仅在当前 SHA-256 仍等于已知 post SHA-256 时恢复精确 preimage；
- config 已被并发修改时 fail-closed，不覆盖用户改动，保留 journal、manifest 和
  backup；
- 已 provision 的 wheel 可以保留，但 plugin 必须恢复为未由 HFC 启用，且源码
  不得残留本次未完成 patch；
- 不输出秘密，不声称“安装成功”；
- 不自动重启 Gateway，只报告 `restart_required`。

## 10. Manifest v3

`manifest_version: 3` 在现有 run/cron/Base ownership 上增加：

```json
{
  "manifest_version": 3,
  "phase": "installed",
  "integration": {
    "mode": "hybrid",
    "capability_fingerprint": "sha256:...",
    "patch_groups": ["..."],
    "plugin": {
      "key": "hermes-feishu-card",
      "entry_point": "hermes_feishu_card.hermes_plugin",
      "distribution": "hermes-feishu-streaming-card",
      "version": "4.3.0",
      "python_identity": "python-sha256:..."
    },
    "plugin_config": {
      "enabled_before": false,
      "added_by_hfc": true,
      "pre_sha256": "...",
      "post_sha256": "...",
      "config_backup_id": "hfc-config-preimage-...",
      "backup_sha256": "..."
    }
  }
}
```

示例省略现有 provenance 和 target hash 字段。安全要求：

- plugin、plugin_config 和 patch-group 字段必须按 group 全有或全无；
- phase 只接受已知状态；
- 路径使用 portable relative representation；
- raw config、secret、chat id 和绝对 home path 不进入 manifest；
- `config_backup_id` 只接受固定前缀、长度和字符集，禁止 `..`、slash、backslash
  和任意路径解释；
- unknown version/phase/mode/group 一律“newer installer required; refusing to
  mutate”。

V4.3.0 能读取 V1/V2 以执行现有恢复。V2 → V3 install 迁移从 verified backup
取得原始源码，根据新 decision 重渲染；不能把 Hybrid marker 叠在旧 Legacy
patch 上。旧 HFC 遇到 V3 必须继续拒绝 mutation。

## 11. Restore、Uninstall 和 Repair

V3 restore/uninstall 的顺序：

1. 读取 manifest/journal/config backup，绑定全部文件与 parent identities；
2. 重新探测 runtime、entry point、config 和 patch targets；
3. 验证 current target hash 等于 manifest patched hash；
4. 从 verified backup 恢复 run/Base/cron；
5. 若 `added_by_hfc=false`，不修改 plugin config；
6. 若 `added_by_hfc=true` 且 current config 等于已知 post hash，恢复精确 preimage；
7. 若 config 已变化、backup 缺失/变更或 binding 改变，拒绝覆盖并保留所有证据；
8. 全部恢复验证通过后才删除 manifest、journal、source backup 和 config backup。

`uninstall` 只撤销 HFC integration ownership，不尝试从 Python 环境 pip uninstall
当前正在执行的包。重复 restore/uninstall 在 clean state 上保持幂等。

Repair planner 增加 v3 phase：

- `prepared`：源码未改时可安全撤销或继续；
- `plugin_enabled`：config 符合 post hash 时可继续 patch 或精确回滚；
- `installed`：走现有完整一致性检查；
- 不认识的 phase、配置漂移、entry point drift、capability drift 或 target drift：
  manual review。

任何自动 repair 仍只设置 restart required，绝不自动重启 Gateway。

## 12. Hermes 更新和模式迁移

Hermes 更新后必须重新探测所有能力，不沿用旧 mode。允许的方向包括：

```text
legacy-patch -> hybrid -> native-hooks
native-hooks -> hybrid -> legacy-patch
```

降级只有在目标模式的全部能力和 anchor 可验证时才允许；否则拒绝 mutation。

迁移流程：

1. 验证旧 manifest、config ownership、backup、Git/provenance 和 current target；
2. 从 verified original 移除旧模式所有 owned marker；
3. 对新 Hermes 重新执行 runtime probe 和 selector；
4. 根据新 mode 重渲染所需 target；
5. 保留最初的 plugin enable ownership，不能把“由 HFC 添加”误写成“用户原有”；
6. 写入新的 capability fingerprint 和 patch groups；
7. 运行 `doctor` 并设置 Gateway restart required。

现有飞书 `/update` maintenance flow 在停止 Gateway 后先走正式 restore，因此也会
安全恢复 HFC-owned plugin config。官方 updater 和 exact HFC wheel 重装完成后，
setup/install 用同一 `HermesRuntimeBinding` 重新启用 plugin并选择新 mode。若
Hermes home、config 或 entry point identity 漂移，maintenance job 以可恢复失败
结束，不猜测目标。

## 13. 诊断和运行时可见性

`doctor --explain` 至少输出：

- selected `integration_mode` 和 reason；
- Hermes plugin API probe status；
- required/available native hooks；
- required/available patch groups；
- entry point distribution、version 和 origin status；
- plugin enabled/effective-disabled status；
- manifest phase/mode/fingerprint match；
- restart required 和精确下一步。

`doctor --json` 使用结构化字段，不输出 raw home、config、chat、session 或 secret。
人类可读路径遵循现有 doctor 安全规则。

`runtime.hello` / heartbeat 和 `/health` 增加：

- active integration mode；
- manifest/capability fingerprint 的短安全摘要；
- plugin registered status；
- patch-group count，不列出本地源码路径。

这些事实只用于 readiness/diagnostics，不构成自动 mutation 权限。

## 14. 测试设计

所有产品改动遵循 test-first。最低自动化覆盖如下。

### Pure unit tests

- selector 的 Native、Hybrid、Legacy、fallback 和 unsupported 组合；
- capability fingerprint 稳定性和未知字段拒绝；
- entry point exact distribution/module/version/origin；
- `IngressBindingRegistry` generation、claim、expiry、并发和 cleanup；
- turn 状态机、started 明确 ACK/拒绝/timeout、terminal reconciliation 和不可
  逆 native-bypass；
- event id、sequence、同 payload dedupe 和 conflict；
- tool sanitizer 不泄漏 args/result/exception；
- approval/session/turn correlation；
- subagent identity 和 preview 边界；
- terminal result single-producer 和 retry；
- worker barrier、terminal 后迟到 item 丢弃和 queue-full fail-open；
- callback 恒返回 `None` 且异常 fail-open。

### Patcher tests

- 每个 Hybrid group 的 anchor、marker body、幂等和 remove；
- Hybrid 不包含 start/complete/tool lifecycle marker；
- Legacy 输出与 V4.2 行为保持兼容；
- Legacy → Hybrid、Hybrid → Native、Hybrid → Legacy 重渲染；
- partial、duplicate、corrupt 和 user-edited marker 拒绝；
- run/Base/cron 全目标可逆。

### Installer/manifest tests

- Manifest v1/v2 restore 和 v3 validation；
- v2 → v3 migration；
- prepared/plugin_enabled/installed crash recovery；
- plugin 原先启用、HFC 新增、explicit disabled 和 alias 状态；
- config post-hash 相符时精确恢复；
- config concurrent change、symlink、parent swap、backup drift 时拒绝；
- entry point hijack、editable import、wrong venv/version/distribution 拒绝；
- `--hermes-home` 与标准 parent layout；
- ambiguous home 和 HFC profile-id 猜测拒绝；
- Windows portable paths 和 PowerShell failure propagation；
- repeated install/restore/uninstall idempotency；
- maintenance updater 保留原始 plugin ownership。

### Runtime integration tests

Hermes v0.20 fixture 覆盖：

- plugin discovery/enable/register；
- ingress → pre_llm → delta/tool → post/on_session_end；
- 一个 turn 一张卡；
- tool start/stop 各一次；
- completion/failed/interrupted 各一个 terminal；

- subagent start/stop；
- native handoff disposition 和 Base ACK；
- Sidecar/plugin 不可用时 Hermes 原生继续。

现有 Legacy fixtures 必须证明旧 Hermes 路径没有行为回归。现有 server、hook、
installer、integrity、process、maintenance、docs 和 package metadata 测试全部保留。

### Cross-platform and release gate

## 15. 实施里程碑

这是一份 V4.3.0 总规格，但实现按以下依赖顺序分段，每段都有 focused gate：

1. **Integration core**：纯 selector、capability model、entry point metadata 和
   package tests；不改变安装或 runtime 行为。
2. **Runtime bridge**：Ingress/Turn registry、official callbacks、event fields、
   Sidecar dedupe 与 subagent timeline；用内存 transport 和 v0.20 hook contract
   测试，不先改安装器。
3. **Hybrid patch**：按 group 重构 patcher、terminal disposition、Legacy 回归和
   v0.20 fixture；证明唯一生产者和全目标可逆。
4. **Installer ownership**：RuntimeBinding、config/journal、Manifest v3、迁移、
   restore/repair/maintenance 和跨平台脚本。
5. **Release convergence**：doctor/readiness、版本、文档、全量 gate 和真实 smoke
   清单。

任何里程碑通过都不等于 V4.3.0 完成；后续层发现前置 invariant 不成立时，回到
拥有该 invariant 的里程碑修正，不在调用层增加补丁掩盖。

## 验收结论格式

交付审计按以下状态报告：

- `IMPLEMENTED`：代码和 focused tests 覆盖；
- `VERIFIED`：完整自动化 gate 有当前证据；
- `REAL-SMOKE VERIFIED`：真实 Feishu/Lark smoke 有当前证据；
- `UNVERIFIED`：缺少平台、凭据或外部环境证据；
- `REJECTED`：任一所有权、去重、fail-open/fail-closed 或恢复 invariant 被违反。

只有所有必需实现和自动化 gate 通过，且真实环境项被诚实标记后，才能称为
“V4.3.0 可发布候选”。Push、tag 和 Release 仍需单独授权。
