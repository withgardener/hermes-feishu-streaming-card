# V4.1 安全控制与排障

这页是 V4.1.1 的运维入口，覆盖按会话原生投递、表格溢出、Hermes runtime 完整性、升级恢复和 sidecar 服务管理。任何输出、日志或 issue 证据都必须遮蔽 chat id、message id、secret、本机路径和 recovery fingerprint。

## 按会话切换投递

单 profile 配置：

```yaml
bindings:
  native_chats: []
```

多 profile 必须把列表写在 `profiles.<profile_id>.bindings.native_chats`；它不继承顶层值。只允许精确匹配，wildcard、regex、prefix 和空值都无效。

```bash
hermes-feishu-card chats use-native CHAT_ID --config CONFIG
hermes-feishu-card chats use-card CHAT_ID --config CONFIG
hermes-feishu-card chats list --config CONFIG
```

多 profile 时三条命令都加 `--profile-id ID`。命令输出只给 masked 摘要，修改从下一条新消息开始生效。若 `POST /delivery/policy` 的 `hfc-policy-v1` proof、配置 reload 或响应失败，hook 必须 fail-open 到 Hermes 原生路径；sidecar 也必须在创建 CardSession 前再次拒绝卡片路径。`/hfc` 管理命令与显式 smoke card 不受 `native_chats` 影响。

Issue #162 的多机器人群聊若依赖 bot-to-bot mention，必须把该群加入 `native_chats`，让 post 创建时就带 `@bot`；被 @ 的目标应用还要开通 `im:message.group_at_msg.include_bot:readonly`、保留 `im.message.receive_v1` 事件订阅，并在新增权限后发布新版本使权限生效。流式卡片在后续 PATCH 中出现 mention，不会补发新的 `im.message.receive_v1`。策略按 turn 固定，不能扫描模型答案后再中途切换。

## 表格与 28,000 byte 预算

```yaml
card:
  table_overflow_mode: compact  # compact | truncate
```

`compact` 保留所有数据：第 6 张及后续 Markdown 表格转成“表格 + 行 + 字段”列表。scanner 忽略 fenced code 中的 `| fake | table |`，也处理 escaped pipe 与 inline code。`truncate` 仅供需要旧行为的用户显式选择。

最终预算按真实序列化 JSON 计算，而不是 Markdown 字符数：最多 5 张 Feishu table、200 个 tagged element、28,000 UTF-8 byte。非终态超限时保留小型等待卡；终态仍超限时先写入无正文、无原始 chat/message id 的 delivery record，再返回 `applied:false, disposition:native`，由 Hermes 原生发送完整答案。已存在卡片的简短 handoff notice 仅在当前进程内异步尝试，不阻塞 native descriptor，也不承诺跨重启修补。

ACK-capable 崩溃恢复只覆盖默认 profile，并要求安装器同时受管 `gateway/run.py` 与 Hermes 0.19 `gateway/platforms/base.py`，由 Base 的真实 delivery ledger 提供 obligation。Hermes 0.19 的 startup recovery 不遍历 secondary profile 独立的 `state.db`，因此 HFC 对 secondary profile 禁用 exact ACK，保持普通 native fail-open。Gateway 与 sidecar 必须同时协商 `native-ack-v2`、`stable-feishu-uuid-v2`、`exact-base-delivery-v1`，且只接受 `hfc-native-handoff-v2` descriptor。descriptor 同时绑定 obligation hash、完整 content hash、已加载 Feishu adapter 及其模块级 planner 依赖的 delivery-plan fingerprint、canonical `create` / `thread-create` route，以及由 default profile、chat、thread 与 route 域隔离派生的 `target_hash`；`hfc-native-handoff-recovery-v2` 五项必须全部命中。私有 handoff state 使用 schema v4，只持久化单向 hash/枚举，不保存正文或原始路由标识。恢复时只发送 ledger 保存的原始 content，不能用 recovered marker 或随机 fallback 文本套用旧 UUID。terminal POST 已提交但响应丢失/损坏时，Gateway 立即用同一五项 binding 查询恢复；两次本机请求都不可用时使用相同五项派生的 provisional UUID seed 保护本轮发送，并在 ledger 标记 delivered 后异步重查完整 descriptor；若最初请求根本没有到达 sidecar，后续启动恢复仍回到带可见 marker 的普通 fail-open，因此不能宣称 exactly-once。

全部逻辑分片成功、ledger 已持久化 `delivered` 后才签名 ACK。飞书的一小时幂等窗口内提供 bounded idempotency；窗口外 exact descriptor 失效，sidecar 将未确认记录标为 `uncertain` 并提示人工复核真实会话，而 Hermes 可继续用带可见 `RECOVERED_MARKER` 的有界上游恢复保护答案不丢失。该路径使用普通随机 UUID，不借用旧 descriptor，也不伪装成 exact 重试。durable record 缺失、冲突或损坏时同样 fail-open，因此不宣称永久 exactly-once，也不宣称任何重复 terminal 永远不会产生第二份答案。exact ACK 只覆盖默认 profile、无附件/媒体的普通文本 final-answer；secondary profile、附件/媒体、Cron 与 direct command 继续使用 Hermes 原生 best-effort/fail-open 路径。

## integrity 模式与升级迁移

```yaml
integrity:
  mode: safe  # safe | notify | off
```

- 新 setup/example 写 `safe`。
- 旧配置缺少该段时按 `notify` 加载，不做自动 mutation。
- `off` 关闭 runtime control plane，但普通事件 auth 和 `doctor` 仍有效。

启用旧安装的 `safe` 前：

```bash
hermes-feishu-card integrity migrate-safe \
  --config CONFIG \
  --hermes-dir HERMES_DIR \
  --yes
```

只有 Git root/ancestry、owned blobs、backup、manifest、anchors 和可逆 patch 全部一致才成功。成功后 `sidecar.restart_required: true`、`gateway.restart_required: false`；先重启 sidecar。之后 runtime 通过 `hfc-runtime-v1` 发送 `runtime.hello` 和 `runtime.heartbeat`。

若 on-disk recovery plan 已是 `installed`，sidecar 等待首次认证 `runtime.hello` / `runtime.heartbeat` 时保持 `runtime_heartbeat_waiting` 或 `runtime_heartbeat_missing`；Gateway 正常重启造成短暂中断时可显示 `runtime_heartbeat_stale`。这些 liveness 状态不是 repair 证据，不得写 restart/manual-review fence；新 matching hello 到达后应一次恢复 ready。

若 safe repair 真的重新安装了 hook，readiness 会改为 `gateway.restart_required: true`。restart/manual-review fence 会以 0600 文件原子持久化到 0700 state dir；修复前 runtime id 仅保存 domain-separated hash，不保存原文。读取与替换同时绑定 state root 及 fence file identity，目录或文件在操作期间被替换会 fail-closed。重启 sidecar 不会清除 fence，旧 runtime 的 hello/heartbeat 与新 runtime 的 heartbeat 都不能绕过。HFC 不会自动重启 Gateway；用户在合适窗口手动重启，只有不同 runtime id 且 generation/package 匹配的新 `runtime.hello` 才恢复 ready。

若修复前没有已认证 runtime，fence 的 `pre_repair_runtime_hash` 为空，runtime 无法自行证明新旧进程。人工审核磁盘状态后，可在 Hermes plan 为 `installed`、sidecar health 不可达且 state dir 内完全没有 pidfile 时执行：

```bash
hermes-feishu-card integrity acknowledge-review \
  --config CONFIG \
  --hermes-dir HERMES_DIR \
  --yes
```

V4.1.0 未绑定 empty-hash fence 只在 `restart=true + manual=true` 的精确已知形态下允许显式迁移；未绑定 non-empty hash fence 始终拒绝。新 fence 以 domain-separated hash 绑定 Hermes target 与 integrity plan，不保存本机路径；state-dir 内私有跨进程锁串行化读取/写入，ack 使用 opaque state token 做 CAS。CLI 会在写入前两次验证 recovery/integrity plan、pidfile 与 health。已绑定 non-empty hash 只解除 `manual_review_required`，必须保留 `gateway.restart_required` 与原 hash，等待不同 runtime id 的 matching `runtime.hello`。任何仍在运行的 sidecar、残留 pidfile、非 `installed` plan、binding/snapshot 变化、非私有/损坏 fence 都拒绝 acknowledge。之后人工重启 sidecar 与 Hermes Gateway，再用 `doctor --explain` 和 `/health` 确认 ready；命令不是绕过 dirty target、branch rewind、symlink、source-stripped evidence 或未知 manifest/backup 的强制开关。

## service.manager

```yaml
service:
  manager: auto  # auto | systemd-user | systemd-system | detached
```

| 值 | 行为 | 权限边界 |
|---|---|---|
| `auto` | 有 user manager 时用 `systemd-user`，否则 `detached` | 不查询 system bus，不调用 `sudo` |
| `systemd-user` | 明确要求 user manager | 不可用即失败，不 fallback |
| `detached` | owned detached process | 跨平台与容器默认安全边界 |
| `systemd-system` | Linux transient system unit | 仅显式 opt-in；不写 `/etc`，不调用 `sudo` |

状态文件记录 manager、unit、token 与 PID。任何 identity 不一致、活进程归属不明或 state-dir symlink 都必须 fail-closed，不得 kill 未验证进程。旧版 `0644` pidfile 只有在当前用户拥有、非 symlink、权限为 `0700` 的私有 state dir 内才能作为迁移候选；读取通过 `O_NOFOLLOW` 打开的 fd，迁移必须绑定同一目录与文件 identity，再原 inode 收紧到 `0600`。目录、inode、内容形状或 health identity 任一变化都拒绝迁移。V4.1.1 detached sidecar 只接受 loopback + process token 的自停请求；响应写完后由进程自身退出，管理端不向数字 PID/PGID 发送 TERM/KILL。运行中的 pidfile-less sidecar、缺少自停接口的旧 sidecar或自停超时均不自动接管/kill，保留状态并要求人工停止后重跑 setup。

`setup/install` 使用检测到的 Hermes runtime venv 安装，并以 `python -I` 隔离复检当前 HFC 包确实来自该 venv 的 `site-packages`。若已有 sidecar，setup 比对 `/health` 报告的 package version 与 Python identity：匹配时保留健康进程，不匹配或陈旧时走受管自停/重启，避免 CLI/磁盘已升级但 sidecar 仍加载旧包。普通 `start` 也必须通过隔离 import 与版本检查；`start/status/stop` 使用同一显式 `--env-file`。完成后仍由操作者在合适窗口人工重启 Hermes Gateway。

Docker Compose 是普通容器流程：setup 完成后启动 sidecar，健康后再启动 Gateway；环境固定 `HERMES_FEISHU_CARD_SERVICE_MANAGER=detached`。发布门禁实际以 `install-docker.sh` 安装并 patch fixture Hermes，随后让 sidecar、Gateway 和 probe 以 non-root 身份运行；已打补丁 Gateway 必须先送达签名 `runtime.hello` 并达到 ready，再经 hook 送达真实签名 `POST /events`。不要在容器中启动 systemd，不要增加 privileged、host PID 或 `/etc/systemd/system` mount。

## 常见排障

| 现象 | 检查 | 安全动作 |
|---|---|---|
| `chats use-native` 后当前卡仍更新 | 当前 turn 的策略已固定 | 等下一条新消息；不要中途切换 |
| 未知 profile 或配置 reload 失败 | `doctor --explain`、配置语法 | 原生消息是预期 fail-open；修复配置后重试 |
| 表格 6+ 变成字段列表 | `card.table_overflow_mode` | 这是 `compact` 的无损兼容渲染；需要旧行为才选 `truncate` |
| 卡片显示 handoff，完整答案是原生消息 | final JSON 超过 28,000 byte | 这是内容保护，不应重发或手工拆掉一半答案 |
| readiness 为 starting/degraded | `runtime.hello` / `runtime.heartbeat` age | 检查 sidecar 与 Gateway runtime 版本、transport state；不把 liveness 当 readiness |
| 首次 heartbeat 尚未到达但出现 fence | on-disk plan 是否已是 `installed` | V4.1.1 等待状态不写 fence；升级后重跑 setup/doctor，不手工改 fence |
| `sidecar.restart_required: true` | 刚运行 `integrity migrate-safe` | 重启 sidecar；此步 `gateway.restart_required: false` |
| `gateway.restart_required: true` | strict repair 已完成 | 选择无活动对话窗口手动重启 Gateway；HFC 不自动执行 |
| `manual_review_required` 且 hash 为空 | installed、sidecar stopped、无 pidfile | 满足全部前置条件后运行 `integrity acknowledge-review`，再人工重启 sidecar + Gateway |
| 运行 sidecar 无 pidfile | 旧进程 identity 无受管记录 | 不自动接管或 kill；人工停止旧服务后重跑 setup |
| setup 后仍显示旧 package/Python | `/health` package/Python identity | 确认使用 Hermes venv，重跑 setup 让受管重启收敛 |
| `systemd-user` unavailable | user manager 是否可用 | 启用 user manager 或显式选 `detached`，不要改成 sudo wrapper |
| Docker 内 systemd 错误 | manager 配置 | 使用普通容器进程与 `detached` |

## Integrity 人工确认边界

`acknowledge-review` 不是通用修复命令。只有当 doctor 同时验证 recovery state 为 `installed`、recovery actions 为空、integrity plan 为 `installed` 且 reason 为 `recovery_not_required` 时，才会建议先停止 sidecar 再确认。其他 manual-review reason 必须先修复报告中的安装状态，再重新运行 doctor。
