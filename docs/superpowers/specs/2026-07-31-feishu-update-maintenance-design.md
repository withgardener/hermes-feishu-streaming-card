# Feishu Private-Chat Hermes Update Orchestration Design

## Summary

Hermes Feishu Streaming Card (HFC) will turn an exact bare `/update` command in
a Feishu private chat into a confirmed, observable maintenance workflow.

The workflow updates Hermes through the official `hermes update --yes` command,
then reinstalls the exact HFC version that was already running, reapplies HFC's
owned hooks through the normal installer, restarts services, verifies runtime
readiness, and reports the result by updating the original Feishu card.

The work runs from an independent maintenance runtime outside both the Hermes
checkout and Hermes virtual environment. This is required because a Hermes
update can replace tracked source files, rebuild its virtual environment, and
restart the Gateway while the operation is still in progress.

This design does not change group-chat `/update`, does not upgrade HFC to a new
version, does not add a custom Hermes rollback, and does not propose any change
to upstream Hermes.

## Problem

HFC currently installs its runtime package into the Hermes environment and
injects small, owned hook blocks into tracked Hermes files:

- `gateway/run.py`
- `gateway/platforms/base.py`
- `cron/scheduler.py`

Hermes' updater fast-forwards or replaces the checkout, may rebuild the Hermes
virtual environment, restores its own stash, and restarts Gateway processes.
Those operations can remove HFC's installed package and replace the files that
contain HFC hook blocks.

The existing HFC command card can render pre-restart `/update` feedback, but it
cannot safely own the complete update lifecycle. The sidecar, Gateway, Hermes
checkout, and Hermes virtual environment are all allowed to disappear or
change during that lifecycle.

The user-visible result is that a successful Hermes upgrade can leave native
Hermes working while HFC is no longer installed or active. Repairing the state
currently requires a separate manual HFC reinstall.

## Product Promise

For a supported HFC installation, a user can send `/update` in a Feishu private
chat, inspect what will change, confirm once, and receive a final result in the
same card.

A successful operation guarantees:

1. Hermes was updated by its official updater.
2. The same previously verified HFC version was reinstalled from a pinned local
   artifact.
3. HFC hooks were regenerated by the normal patcher against the new Hermes
   source.
4. The sidecar and Gateway were restarted from the new runtime.
5. HFC runtime authentication, readiness, health, package version, and import
   origin were verified.

When any safety precondition is uncertain, the automatic update is refused
before mutation or stopped at a recoverable boundary. The card gives a
sanitized reason and an exact safe local recovery command where one exists.

## Design Principles

- **Private chat only:** only an exact bare `/update` in Feishu private chat is
  intercepted.
- **Explicit confirmation:** inspecting availability does not authorize an
  update; a bound, short-lived confirmation click is required.
- **Official Hermes updater:** HFC invokes `hermes update --yes`; it does not
  reproduce Git update logic or invent a second rollback mechanism.
- **Same HFC version:** the operation reinstalls the exact verified HFC version
  present before the update. Updating HFC is a separate action.
- **Independent survival boundary:** the maintenance executor, journal, and
  wheel artifact live outside the Hermes checkout and virtual environment.
- **Evidence before mutation:** HFC-owned files, artifact hashes, process
  identities, checkout state, and update target are revalidated immediately
  before execution.
- **Fail-open for unsupported commands, fail-closed for owned mutation:** group,
  non-Feishu, and unsupported command paths retain Hermes behavior. Once HFC
  recognizes its private update workflow, uncertain mutation is refused rather
  than falling through to an unconfirmed raw update.
- **One card, one operation:** progress and terminal state update the original
  confirmation card. Duplicate clicks do not create duplicate jobs.
- **Local convergence over card delivery:** before mutation, a card update
  failure aborts. After mutation begins, the supervisor completes or safely
  stops local recovery even if Feishu delivery fails.
- **No secret propagation:** credentials are loaded when required and are never
  copied into the job journal or card payload.

## Scope

### Included

- Exact bare `/update` interception in Feishu private chats.
- Read-only update inspection and a two-button confirmation card.
- Initiator-, chat-, operation-, and expiry-bound confirmation tokens.
- A separately provisioned maintenance runtime and pinned HFC wheel.
- Durable, atomic, resumable update jobs with one global update lock.
- HFC-owned hook restoration before the Hermes update.
- Official Hermes update execution and post-update validation.
- Offline reinstall of the same HFC version.
- Hook regeneration, sidecar startup, Gateway restart, and readiness checks.
- Same-card progress, cancellation before mutation, success, and failure states.
- Installer, CLI, diagnostics, documentation, and cross-platform lifecycle
  support needed to provision and operate the feature.

### Excluded

- Group-chat automatic updates.
- Parameterized `/update ...` interception.
- Non-Feishu command interception.
- Automatic selection or installation of a newer HFC release.
- A custom Git reset, checkout replacement, Hermes rollback, or retry loop.
- Overwriting unrelated user changes in the Hermes checkout.
- Raw command output, local secrets, full paths, or identifiers in Feishu
  cards.
- Arbitrary maintenance command execution.
- Changes, issues, or pull requests against upstream Hermes.

## Command Routing and Interaction

### Routing Rules

HFC installs a dedicated wrapper around Hermes'
`GatewayRunner._handle_update_command`.

The wrapper intercepts only when all of these conditions are true:

- platform is Feishu/Lark;
- conversation is a private chat;
- message is the exact bare `/update` command after Hermes' normal command
  parsing;
- sender and chat identity are available;
- the HFC sidecar and external maintenance capability can be authenticated;
- existing Hermes admission and the HFC operations allowlist admit the sender.

Group chats, topics that Hermes classifies as group conversations, non-Feishu
platforms, aliases with different semantics, and parameterized variants call
the original Hermes handler unchanged.

If the request is the recognized private HFC path but identity, maintenance
runtime, artifact, or state evidence cannot be verified, HFC does not call the
original update handler. It returns a failure card with a safe local command.
This prevents a high-risk command from silently bypassing the confirmation
boundary after HFC has claimed it.

### Inspection Card

The first `/update` is read-only. It performs bounded inspection and presents:

- current Hermes version and commit;
- target version or available commit count from `hermes update --check`;
- current pinned HFC version;
- HFC artifact version and integrity status;
- hook, backup, manifest, configuration, and maintenance-runtime readiness;
- whether active HFC sessions must drain;
- `确认更新` and `取消` buttons.

The card does not show raw paths, full hashes, tokens, command output, or
credentials.

`取消` marks the operation cancelled and removes its buttons. It does not call
the original Hermes update command.

### Confirmation Security

The confirmation token is signed and expires after 120 seconds. It binds:

- operation id;
- action type;
- profile;
- private-chat id;
- initiating Feishu operator;
- pre-update Hermes head and update-target evidence;
- HFC version and artifact fingerprint;
- diagnostic and hook-state fingerprints.

Even in private chat, the click must come from the initiating operator. The
click path reruns admission and allowlist checks.

Immediately before accepting the click, HFC recomputes mutable evidence. A
different checkout head, update target, HFC version, artifact, hook state,
active job, or process identity makes the token stale and requires a new
inspection.

The first valid confirmation atomically claims the operation. The card removes
its buttons before starting the executor. Repeated deliveries or clicks return
the current operation state and never start a second update.

## Architecture

### Runtime Components

The feature has four responsibility boundaries:

1. **Hermes hook wrapper:** recognizes the supported command path and preserves
   the original handler everywhere else.
2. **HFC sidecar coordinator:** creates inspection reports, signs actions,
   validates confirmation, and submits a durable job.
3. **Independent maintenance supervisor:** survives checkout replacement,
   virtual-environment rebuild, sidecar shutdown, and Gateway restart.
4. **HFC installer and patcher:** perform the same verified package
   installation and owned hook transaction used by normal setup.

The sidecar never runs the long update in its aiohttp event loop. After an
atomic job claim, it launches or signals the independent supervisor and returns
the in-progress card promptly.

### External Maintenance Layout

The default per-user layout is:

```text
~/.hermes_feishu_card/maintenance/
  runtime/
  artifacts/
    hfc-<version>.whl
    hfc-<version>.json
  jobs/
    <job-id>.json
  lock
```

The maintenance root is private mode `0700`. Artifact metadata, journals, and
lock files are mode `0600`. Writes use a temporary file in the same directory,
`fsync`, and atomic replace.

The maintenance Python environment must not resolve from:

- the Hermes checkout;
- the Hermes virtual environment;
- the active HFC source checkout;
- the current shell's editable-package path.

Its manager boundary is:

- macOS: a user LaunchAgent or an independently launched process whose
  executable and dependencies are outside Hermes;
- Linux: a systemd user service when available, otherwise a verified detached
  maintenance process outside the Gateway service cgroup;
- Windows: an independent maintenance process with a detached process and file
  locking boundary.

If the installer cannot provision and verify that boundary, the automatic
private-chat update feature reports `unavailable`; normal HFC and native group
`/update` behavior remain usable.

### Pinned HFC Artifact

HFC setup stages an exact wheel for the selected install source, for example:

```text
python -m pip wheel --no-deps <selected-hfc-install-spec>
```

The resulting wheel is copied into the private artifact directory only after
package name and version inspection. Metadata records:

- normalized distribution name;
- version;
- wheel filename;
- SHA-256;
- source/install-spec classification;
- creation time;
- provisioning HFC version;
- artifact schema version.

The automatic update accepts only an artifact whose metadata, filename,
embedded package metadata, installed HFC version, and SHA-256 agree.

Post-update installation uses the cached wheel with dependencies disabled and
network access unnecessary. It does not resolve `latest` and does not reuse a
mutable VCS or local-source install specification.

### Durable Job Journal

The job journal contains only the data required to resume safely:

- schema version and job id;
- current phase and bounded attempt counters;
- created, updated, confirmed, and phase timestamps;
- pre-update Hermes version and head;
- inspected target/update evidence;
- HFC version, wheel SHA-256, and artifact metadata reference;
- hook, manifest, backup, diagnostics, and operation fingerprints;
- sanitized service-manager identities;
- private card delivery reference needed to update the original card;
- sanitized terminal result and recovery classification.

It never contains:

- Feishu App Secret, tenant token, state-dir transport secret, or environment
  contents;
- raw chat, message, or operator identifiers when an encrypted/opaque delivery
  reference is sufficient;
- raw command output;
- arbitrary shell command text;
- unredacted local configuration.

The supervisor loads Feishu credentials at execution time through the existing
HFC configuration precedence. The journal may hold the minimum opaque
message-reference fields required by the Feishu API, protected by the private
filesystem boundary, but those values never enter logs, health output, or
diagnostic cards.

Every phase is idempotent. On restart, the supervisor inspects the real
checkout, environment, hooks, processes, and service health before resuming.
It advances only when the journal's expected fingerprint still matches current
evidence. It never blindly repeats a mutation solely because the journal says a
phase was incomplete.

### Global Lock

Only one automatic Hermes update may exist per maintenance root. Job creation
and confirmation both check the global lock. The supervisor owns the lock from
the final confirmation revalidation until a terminal state is durably written.

Stale-lock recovery requires both:

- the recorded supervisor identity is no longer alive; and
- current checkout, artifact, job, and service fingerprints support a safe
  resume classification.

Removing an uncertain lock is a local manual operation, not a card button.

## Update State Machine

The visible states are:

```text
inspecting
  -> awaiting_confirmation
  -> locking
  -> draining
  -> restoring_hooks
  -> updating_hermes
  -> reinstalling_hfc
  -> starting_services
  -> verifying
  -> succeeded | failed
```

`cancelled` is a terminal state reachable only from
`awaiting_confirmation`.

The same Feishu message is updated in place. Buttons are present only in
`awaiting_confirmation`. Progress uses concise, sanitized descriptions rather
than subprocess output.

### Phase 0: Read-Only Preflight

Before showing confirmation, HFC:

1. Runs `hermes update --check` with a bounded timeout.
2. Records current and target versions, commits, and available commit count.
3. Verifies the cached HFC wheel's version, metadata, and SHA-256.
4. Verifies the Hermes root, virtual environment, HFC manifest, backups, hook
   ownership, and installer compatibility.
5. Refuses merge, rebase, unmerged, or other incomplete Git operations.
6. Refuses tracked changes not owned by the verified HFC hook transaction.
7. Allows unrelated untracked files because the workflow never removes them.
8. Checks that no other maintenance job is active.
9. Measures active HFC sessions and Agent work that must drain.

Preflight is advisory until confirmation; all mutable facts are revalidated at
the click boundary.

### Phase 1: Confirm, Lock, and Drain

The valid confirmation:

1. Recomputes admission, update, checkout, artifact, hook, process, and job
   evidence.
2. Acquires the global update lock.
3. Persists the confirmed job atomically.
4. Starts the independent supervisor and confirms supervisor ownership.
5. Removes card actions and enters `draining`.

The supervisor stops accepting new HFC maintenance work and waits up to three
minutes for active HFC sessions and Agent work to become idle. If work remains,
the operation aborts before filesystem mutation and releases the lock.

### Phase 2: Stop HFC and Restore Owned Hooks

The supervisor:

1. Stops the HFC sidecar gracefully through its verified service identity.
2. Uses HFC's manifest, backups, and patcher restore logic to remove only
   HFC-owned hook blocks.
3. Verifies every restored file byte-for-byte against trusted restore
   evidence.
4. Rechecks that no unrelated tracked changes or incomplete Git operation
   exists.

It never edits an installed Hermes file by hand. All source restoration and
later hook installation go through `hermes_feishu_card/install/patcher.py`.

### Phase 3: Run the Official Hermes Update

The supervisor executes:

```text
hermes update --yes
```

It does not pass:

- `--force`;
- `--force-venv`;
- `--no-backup`.

The operation uses a fixed 60-minute timeout. Output is written only to a
private, bounded local diagnostic record; card progress exposes only the phase,
sanitized status, and stable error class.

Hermes may restart the Gateway during this phase while HFC hooks are absent.
That native-only interval is expected.

### Phase 4: Validate Hermes and Reinstall HFC

After the updater exits, the supervisor:

1. Detects the actual checkout head and Hermes version rather than trusting the
   expected target.
2. Verifies the checkout is complete, supported, and free of unrelated tracked
   changes.
3. Verifies the Hermes update incomplete marker is absent.
4. Verifies the new Hermes virtual environment can execute Python and import
   Hermes dependencies.
5. Installs the cached pinned HFC wheel into the new Hermes virtual environment
   without dependency resolution or network access.
6. Proves `hermes_feishu_card.__version__` matches the pinned version.
7. Proves the import resolves from the new Hermes environment's
   `site-packages`, not a checkout or editable source tree.
8. Runs the normal HFC installer against the new Hermes source to regenerate
   backups, manifest, and hooks.
9. Runs read-only diagnostics and requires supported, fully installed hook
   state.

If diagnostics explicitly report a known, verifiable integrity-fence state
whose prescribed resolution is `integrity acknowledge-review`, the supervisor
may invoke that official HFC command after rechecking its fingerprint. It never
edits the integrity fence directly and never acknowledges an uncertain state.

### Phase 5: Start Services and Verify

The supervisor:

1. Starts the HFC sidecar from the new Hermes runtime.
2. Restarts Gateway once more so the newly installed hook is loaded.
3. Waits for authenticated `runtime.hello`.
4. Requires `readiness: ready`, `runtime_ready`, and health `healthy`.
5. Rechecks package version, import origin, hook ownership, manifest state, and
   expected service identities.
6. Updates the original card with the terminal result.

Success reports:

- Hermes old version to actual new version;
- HFC version unchanged;
- HFC hook installed;
- sidecar and Gateway ready;
- validation complete.

The supervisor durably writes the terminal result before releasing the lock.
It retains the last five sanitized jobs or seven days of jobs, whichever is
smaller, and removes older job records without deleting the pinned artifact.

## Failure and Recovery

### Before Filesystem Mutation

Inspection, token, lock, admission, artifact, card-update, or drain failure
causes no source or package changes. The job becomes failed or cancelled and
the lock is released.

### After Hook Restore, Before Hermes Update

If Hermes is still the verified pre-update checkout, the supervisor may
reinstall the same pinned HFC artifact and hooks, restart services, and report
that Hermes was not updated.

If the checkout or restore evidence changed, it stops without guessing and
provides the safe local `doctor`/`setup` recovery commands.

### Hermes Update Failure

HFC respects the updater's own rollback and stash handling. It does not run a
custom `git reset`, `git checkout`, hard reset, or stash mutation.

The supervisor redetects the actual checkout, virtual environment, update
marker, and tracked state. It reinstalls HFC only when the resulting Hermes
state is complete, supported, clean, and matches a verified recovery path.
Otherwise native Hermes is preserved and the job stops for manual inspection.

### HFC Reinstall Failure

The preferred degraded result is a complete native Hermes installation with no
partial HFC patch.

The patcher's own atomic transaction rolls back partial hook changes. The
supervisor verifies no incomplete HFC marker or uncommitted manifest transition
remains. It does not retry a destructive phase in a loop.

### Service or Readiness Failure

A restart or readiness timeout does not trigger another patch transaction.
The job records current service identities and diagnostic state, then reports a
sanitized failure plus the exact supported local status/start/restart command.

### Feishu Card Delivery Failure

Before mutation, inability to update the confirmation card aborts the
operation.

After mutation begins, card delivery is best-effort and cannot stop local
convergence. The supervisor writes the durable terminal result, which later
`/hfc doctor` or a maintenance-status CLI command can display.

### Retry Limits

Each phase has a bounded attempt counter. Resume is evidence-driven, not a
generic retry. A repeated mismatch, unknown process, unsupported checkout, or
uncertain hook state becomes a terminal manual-review result.

## Module Boundaries

### `hermes_feishu_card/hook_runtime.py`

- Install the dedicated original-handler-preserving update wrapper.
- Identify exact private Feishu `/update` requests.
- Send inspection requests to the sidecar with verified command context.
- Preserve original Hermes behavior for every unsupported path.
- Suppress duplicate native gray text only after HFC accepts the update-card
  path.

### `hermes_feishu_card/operations.py`

- Add an update-specific operation type and visible state model.
- Reuse signed action transport, admission, idempotency, and card ownership.
- Keep update fingerprints and durable-job semantics separate from repair and
  restart recovery fingerprints.
- Bind private-chat confirmation to the exact initiator.

### `hermes_feishu_card/server.py`

- Build read-only update inspection reports.
- Create and update the confirmation card.
- Validate and atomically claim confirmation actions.
- Submit the durable job to the external supervisor.
- Never execute the Hermes update inside the aiohttp request or card callback.

### New Maintenance Modules

Focused modules should separate:

- artifact staging and validation;
- journal schema, atomic writes, and compare-and-swap transitions;
- update state-machine decisions;
- supervisor execution;
- sanitized card publishing;
- service/process control;
- recovery classification.

The runner entry point must be importable from the independent maintenance
environment without importing an active Hermes checkout.

### `hermes_feishu_card/cli.py`

Internal and diagnostic commands should include:

```text
maintenance provision
maintenance run --job <private-job-path>
maintenance status
maintenance resume --job <private-job-path>
```

`run` and `resume` are internal execution surfaces guarded by private-file
ownership, schema, lock, and fingerprint validation. They are not arbitrary
remote command endpoints.

### `hermes_feishu_card/process.py`

Reuse existing verified manager, PID, process-token, and service-identity
patterns where applicable. The maintenance supervisor must have a lifetime and
dependency boundary independent from the Hermes Gateway and HFC sidecar.

### Installers and Diagnostics

`install.sh`, `install.ps1`, and supported setup paths:

- build or obtain the exact selected HFC wheel;
- validate and stage it;
- provision the external maintenance environment;
- register the appropriate user-level execution boundary;
- verify that the maintenance runner resolves outside Hermes;
- report feature availability without making normal HFC installation depend on
  automatic-update availability.

`doctor` reports:

- maintenance capability status;
- pinned HFC artifact version and integrity;
- supervisor boundary;
- active/stale job classification;
- safe recovery commands.

Cards show only sanitized summaries. Local CLI output may show private local
paths when needed for recovery.

## Security and Privacy

- Existing Hermes message admission and HFC operations allowlist remain
  authoritative.
- Confirmation is signed, time-limited, initiator-bound, chat-bound, and
  evidence-bound.
- The maintenance root and all job material are private to the installing user.
- No shell is exposed through Feishu. Commands and arguments are fixed by code.
- Subprocess environments use an explicit allowlist and omit unrelated secrets.
- Card, health, and normal logs use stable error codes and sanitized summaries.
- Full hashes and local paths are local-CLI-only unless needed in a private
  diagnostic file.
- The supervisor validates executable paths and package origins before running
  them.
- No card action can remove an uncertain lock, discard Git state, change HFC
  version, acknowledge unknown integrity state, or force an update.

## Testing Strategy

### Unit Tests

- Exact private `/update` interception.
- Original-handler preservation for group, non-Feishu, and parameterized paths.
- Admission, allowlist, initiator, chat, token signature, and TTL binding.
- Confirmation idempotency, duplicate callbacks, stale evidence, and cancel.
- Artifact name, version, SHA-256, metadata, and provenance validation.
- Journal schema migration refusal, permissions, atomic writes, compare-and-swap
  transitions, and bounded retention.
- Lock ownership and stale-lock classification.
- Per-phase state transitions and resume decisions.
- Card sanitization and secret/path/output redaction.
- Fixed command construction without force or network-dependent HFC resolution.

### Integration Tests

Use a disposable fake Hermes Git repository and virtual environment to cover:

- clean successful update;
- checkout and virtual-environment replacement;
- failure injection before and after every mutation phase;
- unrelated tracked edits and incomplete Git operations;
- unrelated untracked-file preservation;
- active-session drain and timeout;
- Hermes updater success, rollback, and ambiguous-result classifications;
- old-checkout HFC restoration after pre-update failure;
- HFC reinstall failure leaving clean native Hermes;
- patch/install/restore round trips;
- supervisor termination and evidence-driven resume;
- duplicate confirmation and concurrent global-lock contention;
- sidecar/Gateway restart and readiness timeouts;
- card delivery failure before and after mutation.

### Platform Tests

- macOS LaunchAgent or independent supervisor boundary.
- Linux systemd-user lifecycle and supported detached fallback.
- Windows process detachment, file locking, and atomic journal replacement.
- Installed wheel import from the intended maintenance and Hermes
  `site-packages` paths.

### Real Feishu Acceptance

- One private-chat confirmation card for one exact `/update`.
- Only the initiating operator can confirm.
- Cancel performs no update.
- One message carries all progress and the terminal result.
- No duplicate gray native command feedback after HFC accepts the path.
- Sidecar and Gateway interruption is visible and bounded.
- The final card reports Hermes changed and HFC unchanged.
- `doctor`, `runtime.hello`, `runtime_ready`, readiness, and health all pass.
- A group-chat `/update` still follows original Hermes behavior.

### Release Gate

Before release:

```text
python -m pytest -q
git diff --check
```

The release must also verify:

- tests at the exact merge SHA;
- sdist and wheel builds;
- isolated wheel installation;
- package version and `site-packages` import origin;
- all GitHub checks green;
- real Feishu smoke on a supported Hermes update.

## Acceptance Criteria

The feature is complete when all of the following are demonstrated:

1. A supported Feishu private-chat `/update` produces a read-only confirmation
   card and never mutates before a valid bound click.
2. Unsupported command paths preserve the original Hermes handler.
3. The supervisor continues correctly while the Hermes checkout, virtual
   environment, Gateway, and sidecar are replaced or restarted.
4. The official Hermes updater is the only component that changes the Hermes
   baseline.
5. The exact pre-update HFC version is reinstalled from a verified offline
   wheel.
6. Unrelated tracked changes are refused and untracked files are preserved.
7. A successful job ends with fully installed hooks, authenticated runtime,
   ready/healthy services, and same-card confirmation.
8. Every injected failure reaches either no mutation, restored old HFC, clean
   native Hermes, or a clearly classified manual-recovery boundary.
9. Journals, cards, logs, and diagnostics expose no secrets or raw command
   output.
10. Unit, integration, platform, full-suite, package, exact-merge-SHA, and real
    Feishu acceptance gates pass.
