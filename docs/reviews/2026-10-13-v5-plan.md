## 目标与取舍

这一轮让用户在任务开始、等待、交互、完成和失败时都能理解状态并完成操作，同时让维护者能以较小成本定位故障、验证修改和跟进 Hermes。

- 正确性：答案和授权范围完整；身份、终态及执行次数不因重试、更新或恢复而混乱。
- 体验：卡片有清楚的阅读主次，点击有反馈，长内容可回看，新用户能确认设置是否生效。
- 健壮度：局部故障有界降级，未知结果不冒充成功，维护动作不会打断未确认空闲的运行环境。
- 可维护性：明确模块边界、可回放的回归场景、可解释的错误，以及可回收的验证环境。

默认排序权重为正确性与可靠性 35%、日常体验 30%、维护收益 25%、交付成本 10%。这是用于讨论取舍的工程判断，不是用户调研评分；内容丢失、错误授权、跨用户更新和破坏生产环境属于硬约束，不能用其他收益抵消。复杂度没有证据时先做小试验，不编造精确收益或工期。

推荐分阶段交付：每个用户体验改动带上必要的内部边界整理。集中重写全部协调器会放大回归范围；只加界面开关又不能降低维护成本。

### A · 故障、回放与资源治理

**交付内容**

- 建立脱敏的合成事件轨迹，覆盖首事件缺失、重复、乱序、晚到、超时、断连、终态更新失败、重启展示恢复，以及同群多用户/多 profile 隔离。先复用现有案例，再补组合缺口。
- 区分任务执行状态、交互处理状态和消息投递结果。例如“选择已记录”不等于任务完成，“已尝试发送”不等于已送达。每条关键转换记录稳定原因码和可关联的非敏感操作编号。
- 来源检查内部区分 Git 不可用/超时、commit 不匹配、脏目录、snapshot 构建失败、摘要不符和 PluginManager probe 失败；对已有外部协议保持兼容，新增原因需要版本化。只增加可解释性，不减弱 fail-closed。
- 给临时资源登记 operation、创建者、用途、可回收条件、字节数和必要保留期。共享固定源码按 SHA 复用且保持不可变；缓存命中不能跳过真实性验证。
- 测试成功后保留摘要、哈希和必要日志，回收 pytest 大目录与退役环境；异常和中断也有有界收尾。清理必须核对归属、活跃引用和符号链接，不扫描删除未知目录。

**验收**：同一轨迹重复执行结果一致；重复点击不会重复解析；终态不回退；丢失响应不会重放审批事件。每种来源失败注入得到对应内部原因。连续三轮测试及一次中断后，已退役的大型目录不累积，任务目录与系统 tmp 都有清单。建议任务临时占用先设 2 GiB 软预算，超过后停止新建副本并解释；基线测量后调整，不自动清理生产或共享环境来腾空间。

### B · 交互可靠性与回看

**交付内容**

- 统一待处理、提交中、已接收、已失效、拒绝和结果未知的语义；逐一落实审批、clarify、`/new`、模型选择、会话选择等现有入口。平台不支持某状态表现时选可验证的降级，不假设按钮都能实时禁用。
- 为“点击到了哪一步”提供内部检查路径：SDK 收到 → HFC handler → 身份校验 → 原 Hermes resolver → 原卡回执。外部用户只看到能理解的原因和有效下一步。
- 提交响应丢失时只查询既有请求状态。无法确认时说明未确认；不能提示用户反复点批准，也不提供绕过 owner/过期校验的“重试”。
- 正文保留问题与完整操作范围，批准和拒绝同样可发现。用户输入及多选状态不因流式刷新消失；交接后的旧卡保持正文和决定记录。

**验收**：长范围、多选输入、双击、慢网、响应丢失、错误操作者、过期、侧车重启、续答换卡分别有正常/拒绝路径；验证 resolver 的实际调用次数。桌面和真实移动端分别操作；截图只证明布局。#374 固化为真实 SDK/adapter 回归，报告者结果单独登记；#344 未复现前不写“原问题已修复”。

### C · 视觉体系与动态阅读

**交付内容**

- 先用相同的完整内容比较两种平台可实现的方向：**正文优先**（状态占用少、过程收起）与**任务分区**（状态、正文、操作、历史分组更明确）。比较短答、长工具、长审批及完成卡，不只比较一张短答案。
- 建立共享的视觉角色与组件规则，覆盖普通 JSON 2.0、legacy 交互卡、CardKit；状态语义一致，允许平台布局差异。只使用已确认支持的字号、颜色、间距和组件能力，不依赖任意 CSS、字体、粘性按钮或猜测客户端类型。
- 运行中突出当前可观测动作，待输入突出问题/范围/操作，完成后优先正文，失败保留已产生的结果与原因。状态、动作各有一个主要展示位置。
- 正文使用可读字号；过程降低一级；页脚进一步弱化。分隔线只服务真实分组，短答不套空面板，模型和指标不抢主强调色。长标签、长路径和放大字号不能靠缩小文字解决。
- 折叠、滚动和表单尽量保持稳定。优先 coalesce 无需立即展示的中间帧；终态与交互反馈有优先级。没有新事实时不增加装饰性刷新。

**验收**：每个样本检查布局逻辑、主次、字号、颜色、间距、密度、内容完整性、按钮关系和连续帧稳定性；单项阻断不能用平均评分抵消。保存前后同条件证据。桌面普通/窄聊天区域，Android、iOS，浅/深主题与默认/放大字号分别登记适用范围；先覆盖所有关键状态，再按高风险组合补全。没有设备就明确未验证。

**默认策略**：保留已有显式配置与旧预设。新安装可先明确推荐 task 并提供预览；是否变成缺省值，要在候选试用后单独确认并提供回退。原生表格在多端长内容矩阵通过前保持默认关闭。

### D · 内容完整性与长结果回看

**交付内容**

- 把 canonical answer、显示投影、分段与投递计划分开；表格/代码/折叠转换只能改变表现，不能覆盖原始答案。先抽取小的内容决策边界，避免一次性替换整个 Markdown 处理器。
- 统一选择原生表格、Markdown、结构分段和既有完整内容交接的条件；用完整内容片段身份验证覆盖顺序、无遗漏与无重复。保留已有共享字节/元素/表格预算。
- 完成卡提供稳定的结果区、相关附件和可回看的过程入口。交接到另一条消息时，仅在实际目标已投递且平台支持时提供导航；失败时保留明确状态。不能编造消息链接或从正文自动生成可能误导的“结论”。
- 对超宽表格、长单元格、长代码行、嵌套列表和中英混排准备固定样本。局部转换不适用时保留原文，不全局退化，也不靠省略尾部通过视觉验收。

**验收**：1,199/1,200/1,201/5,000 字符等既有边界继续保留，并增加混合结构、转义、Unicode、拆分位置和容量组合回放。静态与流式终态交付内容一致；完整交接失败不能标为已送达。真实客户端能找到、滚动到并复制关键长内容，移动端逐项核验。

### E · 配置和新用户上手

**交付内容**

- 在现有 `card-config` 上增加“文件下次加载值 / 当前进程确认值 / 差异 / 来源 / 是否需重启”的只读对照。运行证据必须绑定实际 HFC 版本、runtime generation 和已授权作用域；不可用时显示未知，不能把磁盘文件当作已生效。
- 收敛用户入口为“选阅读预设 → 看同内容预览 → 看配置差异 → 按明确方式应用”。第一批生成最小 YAML 差异，不增加另一套在线配置服务。写配置能力若进入范围，必须有原子写、备份、作用域确认与失败保持原状。
- 将常用设置与高级兼容设置分组，解释被 profile/bot 覆盖的原因。复制完整示例后显式值覆盖预设的情况要能发现。
- 完善新用户从已接通机器人到第一张可操作卡片的短路径；诊断没接通、无回调权限、运行配置未加载这类不同阶段，不能一律推荐重装。

**验收**：global/profile/bot 覆盖及重置与真实 renderer 一致；不向群卡或诊断报告泄露其他账号/路由配置。找 5 名首次使用者进行任务式试用，目标是在 Hermes/飞书已接通的前提下 10 分钟内选好预设、看懂一次交互、解释是否已生效；这是待测目标，不是现有成绩。

### F · 诊断与可信指标

**交付内容**

- 将诊断组织为影响、证据、原因、下一步，区分环境不支持、完整性需复核、运行代际不一致、点击未到达和投递未知。复用 health/status/doctor 的事实，不建立第二套健康判断。
- 提供字段白名单的本地报告预览与导出：版本、能力、失败阶段、聚合计数和脱敏关联信息；不默认包含正文、配置原文、token、真实用户/聊天 ID 或日志整包，不自动上传。
- #392 先定义指标范围。整轮耗时包含工具和等待；首末 delta 之间可能有多次模型调用，也可能漏掉首 token 和最后 token 的生成时间。总 output tokens 与最终答案窗口未必对应，不能仅相除就标作“纯生成速度”。
- 优先做可解释的阶段耗时和观测首字延迟。后者从 HFC 收到有效的本轮开始事件计至首个答案 delta；缺少开始证据时省略，不称作模型 TTFT 或客户端可见时间。只有 token 数和时间都能绑定相同模型调用时才显示该调用速率；多个调用按一致规则汇总。使用观测窗口时明确标为观测速率，数据不全时省略。纯字符估算的实时速率作为后续可选项，带估算标识，默认不增加视觉噪声或专门 PATCH。

**验收**：单次/多次模型调用、工具间隔、reasoning 与 answer 分离、切模型、零 token、时钟变化、重试和无流式数据都有定义；未知指标不显示 0 或伪精确数字。内部计时用 monotonic clock，墙钟仅作时点展示。诊断包通过合成秘密注入检查；具体 API 失败可定位但不泄露正文。

### G · 按边界改进代码与开发反馈

具体切口、状态写入归属、第一轮三个 PR 及删减标准见[代码减负方案](2026-10-13-code-surgery.md)。先固定行为，再用只读报告拆分验证方法，随后进入终态投递边界；不一次重写协调器。

**分离顺序**

1. 固定来源验证/交互路径的结构化结果与诊断契约；先通过只读 CLI 报告提取验证拆分方法，再进入运行状态边界。
2. 从 `server` 的事件协调路径抽出纯状态转换与副作用计划。锁内只提交必要状态，锁外执行 Feishu I/O；不能因拆文件改变原有终态和投递顺序。
3. 从 `hook_runtime` 分离 Feishu callback 适配与命令呈现，保留一个原 Hermes resolver 和一个事件 producer；无需改协议即可验证时不新增协议。
4. 将 `presentation.py` 逐步从成品 JSON 的递归修改转向明确展示模型和小组件；新增显示行为先进入模型，再由各方言渲染。
5. 按安装、诊断、进程和维护命令分离 CLI handler；patcher 按已验证源码家族组织适配，不使用过于宽泛的匹配覆盖未知上游。

**开发工具**：先在新提取的边界引入 Ruff 的确定性错误检查及 mypy 增量类型检查；不全仓格式重排，也不把所有 `Any` 一次改掉。区分 IM message ID、CardKit entity ID、turn ID 与 callback token，先覆盖真实易混淆边界。新增测试依赖以具体收益为前提；可先用有固定 seed 的事件生成和标准库回放验证不变量。

**验证入口**：补全 preflight 的声明式职责映射，新增模块必须有测试组或明确豁免理由；rename/delete 继续纳入。受控传入并核验上游 fixture，不通过继承生产 HOME 绕过隔离。测试时钟可注入，等待基于状态/事件而不是任意 sleep；首轮失败保留原因、fixture 身份与耗时后再决定是否重跑。

**验收**：每次提取对相同事件轨迹比较响应、状态、payload 和调用次数；新模块依赖方向有检查。关键安全/生命周期分支逐项有案例，覆盖率仅辅助发现缺口。先测十次同类改动的反馈耗时，目标聚焦反馈不超过 5 分钟；完整发布矩阵保留，是否分片取决于资源和 fixtures 复用证据。

### H · 支持矩阵、升级与发布

检查时 Hermes 官方 release 为 [v0.21.7](https://github.com/NousResearch/hermes-agent/releases/tag/v0.21.7)，main 为 [`f7b26efc2ffa`](https://github.com/NousResearch/hermes-agent/commit/f7b26efc2ffa9c1380a7b8c3fad8c7331ab802e3)，其 `pyproject.toml` 仍声明 `>=3.11,<3.15`。这是本轮观察，不是 HFC 已通过这些提交完整兼容测试的结论。实施时重新固定 stable/main SHA 与 SDK，再做能力证明和实际子进程验证。

HFC 仍声明 Python >=3.9；Python 3.9/3.10 已结束官方支持。[Python 生命周期](https://devguide.python.org/versions/) 建议下一主要版本评估收敛为 3.11–3.14，开发基准继续复用已验证环境，3.15 暂不自动纳入。先验证普通 wheel、最低依赖、hook 所在解释器及独立 sidecar 的矩阵，再改声明；提供旧环境检测、迁移和回退记录。若没有明确支持范围或配置迁移，就按兼容版本交付，不强造破坏性变更。

升级验收覆盖“PM 重建环境但旧 sidecar 仍存活”、Gateway 空闲而 Desktop 忙、安装中断、重启失败和配置漂移。必要动作复用现有 owner/drain/恢复机制；证据不足时停止 mutation 并解释，不能自动 acknowledge-review 或强制停止。

发布记录须将代码实现、源代码测试、普通安装、真实 API、实际 Gateway/model 流程及各客户端视觉分栏登记。公开包更新与本机生产部署分别记录；前者完成不能自动勾选后者。代码版本、README、当前路线与验收链接由同一份发布清单核对，历史报告保留日期。

## 实施顺序与可评审批次

以下是工作拆分，不是日历工期。每批进入下一批前提交结果和未通过项；两批后按实际改动量、CI 耗时及设备可用性再估算后续容量。

| 批次 | 范围与独立评审单元 | 出口 |
| --- | --- | --- |
| 0 · 计划与基线 | 本文；固定现有九状态及新增高风险样本；同内容视觉方向；#374 证据归档与 #392 指标契约 | 计划范围及视觉方向明确；实现/验收/未验证状态分开 |
| 1 · 可靠性基础 | 来源错误分类与可复现失败；事件/交互回放；preflight 映射；测试资源收尾。分别成小 PR | 首轮失败可定位、聚焦测试可选择、临时占用有上限；不更改用户默认 |
| 2 · 交互和视觉主线 | B/C 的状态与组件、慢网反馈、旧卡历史保留、长内容投影；提取对应展示边界 | 同内容比较与核心桌面真实交互通过；移动端失败继续修订 |
| 3 · 设置与排障 | 已加载配置对照、新用户流程、诊断预览；满足数据契约时加入完成卡指标 | 5 人试用记录；诊断可用且不泄密；指标不混计时范围 |
| 4 · 候选与发布 | 支持矩阵、升级回退、性能/资源基线、多端验收、公开安装与发布清单 | 所有承诺范围有证据，或明确缩小范围并保留剩余项；取得发布授权 |

不把重大架构重写留到最后一批，也不要求先完成全部重构才交付体验。当前批次内最多保留一个正在实现的功能包和一个验证/兼容包；明确的数据丢失、授权或无法交互问题可以插队，其他增强进入下一批。每次插队后更新被推迟的工作与原因，避免路线再次被维护版本吞掉。

## 统一验收与跟踪

| 层次 | 要证明的事 | 记录方式 |
| --- | --- | --- |
| 内容与权限 | 场景矩阵中无答案/范围静默丢失、无重复解析、无跨用户改卡、无伪成功 | 事件回放、边界生成、resolver 次数、真实拒绝与成功路径 |
| 视觉与交互 | 主要内容可读、动作可理解，输入/滚动不被破坏，失败有解释 | 同内容前后截图 + 实际操作；按客户端/主题/字号登记，不以截图代替点击 |
| 性能 | 在固定硬件、同轨迹、同外部模拟延迟下测解析/渲染/锁等待、PATCH 次数及峰值内存 | 基线与候选各重复采样，p50/p95；先测再设阈值，候选目标 p95 不劣化超过 10%，外部 API 延迟单列 |
| 资源 | 并发 1/5/20 个合成会话与重复生命周期后，队列、重试、缓存、文件和进程均有明确上限 | 隔离环境短压测和持续运行记录；未实测不声称“内存无泄漏” |
| 安装与兼容 | 来源可证明、旧环境可拒绝/迁移、失败可恢复、生产忙时不强停 | 普通 wheel、实际子进程、固定 upstream/SDK、升级回退故障注入 |
| 发布 | 精确 commit/tag、CI、资产校验与公开安装对应同一内容 | 既有 release playbook；保留失败/重跑及未覆盖记录 |

每项工作记录 `范围 → 待实现 → 源码验证 → API/流程验证 → 客户端验证 → 已发布`，不适用项写理由；真实客户端按 macOS/Android/iOS 分列。未通过的项目不能被“CI 通过”或“已经发布”覆盖。维护者负责状态更新与证据回读，Bailey 决定产品/视觉方向及发布范围，外部报告者的证据注明版本和场景。

本轮没有采集新客户端截图、操作飞书前台、更新 Hermes、发送 issue 回复或发布任何版本。美观收益、首屏理解速度、上手时间和性能改善均为待验证目标。实施中的后台 CLI/API 优先；必须使用前台做真机操作时，另行安排不影响使用的验收窗口。

## 暂不纳入

通用管理后台、数据库/消息队列改造、第二套 agent 或审批系统、自动续跑旧任务、永久聊天归档、默认实时字符估算速率、无人确认的自修复，以及为凑版本号重写语言/框架。这些尚无足够收益或安全边界证据，会拖慢本轮清楚可验的交付。
