# HFC 代码减负方案

状态：规划，未修改运行代码。基线是 v4.7.7 / `e03c57369503b3364313bf005d7f0e5087650557`，衔接[下一阶段计划](2026-10-13-v5-plan.md)。目标是降低一次修改牵动的职责和验证成本；物理行数只作信号。

本文是[完整重构与升级执行计划](../plans/2026-10-13-refactor-upgrade.md)的切口说明；总体实施顺序和进度以总计划为准。

## 诊断与切口

| 现有位置 | 观察 | 拆分目标 |
| --- | --- | --- |
| `hook_runtime.py`，12,252 行 | 事件提取、协议传输、adapter 包装、命令和 callback 共存 | 保留稳定 hook 入口；把协议适配、命令交互和事件构造分开 |
| `server.py`，8,935 行 | `_apply_event_locked_inner` 1,266 行，直接访问 9 类 `request.app` 状态；嵌套协程还处理更新、重试和终态恢复 | HTTP 入口负责校验与调度；业务判断接收显式上下文；投递执行与结果提交分开 |
| `cli.py`，6,510 行 | 安装、诊断、进程控制、恢复与格式化入口集中 | 保留 CLI 参数/退出码；先分离只读报告，再分离生命周期与安装事务 |
| `install/patcher.py`，5,395 行 | 多个已验证源码形态及 patch/apply/restore 逻辑 | 复用已有 descriptors、renderers、decomposed 模块，按明确源码家族收敛适配；未知布局继续拒绝 |
| `presentation.py` | 对生成后的 JSON 深拷贝、递归寻找并改写组件 | 逐步把显示意图移到明确展示模型，渲染一次形成组件；保留各卡片方言和容量回退 |
| 部分测试 | 在 `cli` 等协调器上 monkeypatch 私有函数及模块级 `os/subprocess` | 为外部 I/O 提供窄接口；移动代码时验证故障注入仍命中实际路径 |

以上是静态观察，不证明内存泄漏、死锁或性能退化。9 类状态只统计该函数直接访问，未统计被调用函数的间接访问；不能把它解释为全部依赖。

## 先明确谁有权修改状态

| 状态 | 目标唯一写入边界 | 其他模块如何使用 |
| --- | --- | --- |
| turn 身份、sequence、任务终态 | 事件应用/会话状态层 | 读取有版本的快照，提出更新；不能自行改成 completed |
| 交互 pending、claim、resolved、expired | 原 Hermes handle 与 HFC 既有交互协调边界 | renderer 只显示；HTTP/SDK 适配器只归一化输入，不另建授权队列 |
| 卡片 message/entity 身份、generation、投递结果 | 投递协调边界 | 每次外部操作携带准确目标，结果返回后重新核验归属 |
| 展示模型、折叠与视觉角色 | 只读展示计算 | 不修改任务执行状态、授权或 canonical answer |
| 安装清单、服务归属、恢复事务 | 现有安装/维护事务 | doctor 读取和解释；任何写入沿用原子性与可逆验证 |

身份类型首先区分 IM message ID、CardKit entity ID、turn ID 和 callback token。类型标注辅助发现误用，真正的合法性仍需边界运行检查；一个 `NewType` 不构成授权证明。

不把整份 `request`、`app` 或几十个字典包装成一个万能 context 再传给所有模块。每个边界只获得必要数据及少量操作接口；需要什么依赖就明确列出。

## 目标调用关系

```text
Hermes/SDK/HTTP 适配 → 已验证事件 → 会话状态决策
                                      ↓
                             明确的投递/更新计划
                                      ↓
                            展示模型 → 方言渲染与预算
                                      ↓
                              Feishu I/O 执行
                                      ↓
                          核验归属后提交投递结果
```

沿用 Python 模块、dataclass 和现有异步调度，不新增消息总线、通用工作流引擎或服务。`CardSession.apply()` 已承担部分状态决策，`render_options`、`delivery_policy`、`runtime_interaction_transport` 等已有边界应复用；提取前先确认现有模块能否容纳该职责。

`server` 第一阶段仍做协调，只逐项取出独立职责。最终它可以组装这些能力，但业务模块不反向导入 `server`。展示层不访问文件系统、网络或进程管理。生命周期及恢复中的受控持久化与提交顺序要保留，不能机械地把所有文件写入移到锁外。

## 第一轮三个可独立回退的 PR

### PR 1：固定行为与依赖边界

- 为准备拆分的路径整理事件轨迹：重复终态、终态后晚到事件、同 key 的新 generation、交互 pending 时更新、丢失响应、旧卡续答及同群不同操作者。
- 记录输出响应、规范化 payload、状态变化、外部调用顺序/次数与内容完整性。固定时间和随机源；不能把身份、sequence、generation 或授权差异当作噪声抹掉。
- 补全涉及模块的 preflight 路由。给将要提取的模块设置依赖约束，防止反向导入协调器。
- 基线中已知错误单独建失败用例，随后在行为修复 PR 解决；等价性测试不能成为保留缺陷的理由。

出口：相关场景可重复运行、失败可定位，测试故障注入触及真实执行路径。此 PR 不调整运行行为。

### PR 2：用只读边界试运行拆分方法

- 先提取 `cli` 的 doctor 报告格式化/原因解释；复用现有 `diagnostics.py` 的相关能力，职责不同才新增模块。
- 显式传入报告数据，保留公开 CLI 参数、返回码和文本契约。需要更好的文案或新原因分类时，另列行为变化。
- 仅保留确有外部调用或兼容需求的入口委托；内部调用迁移完成后删除临时转发层，不长期保留两套实现。
- 验证普通 wheel 中的导入与 CLI 子进程；仅 checkout 内运行成功不足以确认模块移动完整。

出口：报告格式化可脱离运行环境独立测试；新增模块不反向依赖 `cli`；原有行为一致。此步不涉及安装、启动或恢复 mutation。

### PR 3：分离终态投递操作

选 `server._apply_event_locked_inner` 内 `_render_and_update` 的**终态投递分支**做第一个高价值切口，先保留其他事件路径。当前代码已经安排锁外 Feishu I/O，本次把隐含契约变成显式输入和结果，不重新发明投递流程。

- 在既有锁内记录接受该终态的 session 身份、turn/generation、路由、message ID、内容/渲染决策和预算；需要实时重算的展示项单独标识。
- 锁外执行已有 PATCH、有限重试与终局恢复逻辑。复用稳定 UUID、超时和原生抑制策略，外部结果明确区分已送达、失败与未知。
- I/O 结束后按现有串行化契约核验 session 对象/身份及 generation，再提交对应结果。旧轮晚到成功不能覆盖复用相同 key 的新轮。
- 保留现有审批回执清理、可选额度查询和内容预算顺序；可选显示失败不能阻断最终答案。

出口：上述内容完整性、重复执行、旧轮污染、输入稳定与终局恢复轨迹全部通过；临界区和调用顺序有针对性断言。若无法在单一边界内完成，先缩小为纯判断提取，不把一个 PR 扩为整个状态机重写。

## 后续切除顺序

1. **交互输入与决策。** 将选择解析、身份前置条件、过期判断抽成窄函数；原子 claim、resolver 调用与结果提交继续按原 owner/锁契约工作。
2. **hook callback 与命令适配。** 保持已注入 hook 的稳定公开入口；拆出 SDK 方言和命令上下文，不改变 callback 注册身份或 producer 选择。
3. **展示生成。** 先挑短答案和完成态，将 JSON 后处理转为展示模型；每种方言分别对照。审批/表单随后迁移，避免第一刀同时改变交互和视觉。
4. **维护与安装。** 将检查、计划、受保护的执行与结果核验分离；复用现有事务。patcher 最后按源码家族继续整理，逐字恢复、漂移拒绝和安装幂等必须保留。

每一项优先与实际功能包一起推进；完成一个边界再进入下一个。结构提取与视觉/协议/默认值变化分开评审。

## 可以删什么，必须保留什么

- **确认不可达且无支持契约的代码**：用调用链、动态入口、entrypoint、生成的 hook、配置和测试共同检查。仅靠全仓文本搜索没找到引用不能证明可删。
- **重复实现的规则**：先列输入、输出、失败与兼容语义；只有契约相同才合并。名字相同的“失败”或“恢复”可能属于不同状态层。
- **退役兼容分支**：建立支持矩阵，确认对应 Hermes/SDK 版本退出支持，提供迁移和回退记录后删除；公共安装缺少遥测，不能用“最近没 issue”证明没人用。
- **临时委托与旧实现**：每次提取记录清退条件。迁移结束后移除旧实现，避免新旧逻辑同时维护。
- **必要保护**：来源指纹、归属校验、错误拒绝、重复事件防护、完整内容交接和历史贡献不能为了变短而删除。`legacy/` 仍按现有规则保持归档，本计划不授权修改它。

不要把所有相似代码都做成基类、注册器或 `utils.py`。少量语义不同的重复，比依赖隐式规则的统一抽象更容易维护；是否提取以职责和变化原因决定。

## 怎样证明手术有效

| 指标 | 判定方法 |
| --- | --- |
| 职责清楚 | 新功能有明确归属；展示改动无需进入安装/权限代码，普通兼容适配不改 renderer |
| 状态安全 | 重要状态由指定边界提交；身份和 generation 在异步结果回来时仍核验 |
| 依赖受控 | 新提取的业务模块不导入 `server`/`cli`；新增循环依赖阻止合入 |
| 测试独立 | 状态/展示测试可在无 aiohttp app、无本机 Hermes、无网络条件下运行；实际安装/I/O 另有集成检查 |
| 修改集中 | 记录接下来 5 次可比改动触及的业务模块、验证耗时和返工；测试/文档与生成文件单列，不人为限制必要修复 |
| 运行不倒退 | 固定轨迹下检查 payload、调用次数及容量；并发和失败注入检查顺序；按基线比较 p95 与内存，尚未测量不承诺降幅 |
| 代码减少有意义 | 删除重复决策或退役实现，临时委托按期清退；总行数可能短期增加，不设“砍掉 30%”之类验收指标 |

对新提取代码增量启用 lint 和类型检查，范围清楚且不重排全仓。新函数超过约 100 行、新业务模块超过约 600 行作为人工复查提示，不是机械拆分红线；先核对它是否混合了不同的变化原因。大协调器停止接收新的独立业务职责，紧急修复后登记整理项。

## 回归与回退规则

- 每个 PR 只提取一个职责；保留公开 CLI、事件协议、持久化 schema、默认配置及 hook 入口。必须改变时另做迁移 PR。
- 旧/新逻辑对照仅限无副作用决策，在隔离测试中使用冻结输入运行；不得双发网络请求、双解析审批或启动两套生产侧车。
- 比较同一批轨迹的结果和副作用计划，再跑受影响集成；大幅运行逻辑调整及发布仍执行完整套件、固定上游矩阵与普通安装验证。
- 纯内部重构预期外观不变；若卡片 payload 有预期外差异，停止并解释。改变展示/交互时重新做对应真实客户端验收，不能沿用旧截图。
- 保持每个提交可回退，不混入依赖大升级和 schema 迁移。故障或证据不足时停止下一切口，先定位当前边界。
- 复用现有环境与固定源码，测试结束按归属清理；不为每个小 PR 留一个 venv 或源码快照。

本轮只是把切口、契约与验证路径具体化，未宣称这些结构已经建立，也未执行生产操作。
